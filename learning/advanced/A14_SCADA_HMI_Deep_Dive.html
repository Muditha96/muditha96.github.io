The Screens Were Green. The Reservoir Overflowed.

A REGIONAL WATER SCHEME, THE FIRST HEAVY RAIN OF THE MONSOON

Eighteen remote sites — boreholes, booster stations, reservoirs, a chlorination plant — each with an RTU, all reporting to one control room over a cellular APN. About 230 tags per site, 4140 in the master database, and a specification that says “1 second scan” because that is what the operators asked for.

On the first wet night of the season the control room goes strange. Values stop updating, then update, then freeze again. Comms-fail alarms arrive in bursts of forty. Two operators start running pumps by telephone and judgement. By 03:00 one reservoir has overflowed for ninety minutes and a borehole pump has run dry long enough to damage its bearings. In the morning the SCADA vendor is blamed and the cellular operator is blamed, and both are innocent.

The system was never capable of a 1 second scan, on any night, wet or dry. The master polls sequentially over a single channel. Each site needs three Modbus transactions (two register blocks plus one coil block), and each transaction costs a round trip:

18 sites × 3 transactions = 54 transactions per full cycle fair weather: RTT 200 ms + 30 ms device time = 0.23 s each cycle = 54 × 0.23 = 12.4 s (specified: 1 s) heavy rain: RTT degrades to 600 ms cycle = 54 × 0.63 = 34.0 s comms watchdog: 5 s → every site looks DEAD every cycle, and the operators get a wall of comms alarms and a screen full of stale numbers. BANDWIDTH WAS NEVER THE PROBLEM: one cycle moves about 19 kB, i.e. ~152 kbps at 1 s — trivial for 4G. The link had plenty of bandwidth and no time. Latency × transaction count is the budget that matters.

Three design faults compounded. Polling design — everything in one class at one rate, polled sequentially (page 4). No store-and-forward — the RTUs buffered nothing, so every gap became a permanent hole in the historian (page 8). And the one that actually caused the overflow: the HMI drew a stale number exactly like a live one. There was no indication anywhere on the screen that the value being trusted was thirty seconds old (page 7 and page 9). The operators were not careless. They were misled by a display that could not say “I do not know”.

⚡ PREDICT FIRST

Before reading on — which single change would have prevented the overflow?

B. Every other fault on that list is a performance problem; this one is a truth problem. The reservoir overflowed because a human being made a decision from a number they believed was current. Grey out the value, show its age, and the operator’s behaviour changes instantly — they go and look, or they run the site on its local logic, which is exactly what you want them to do when the telemetry is blind. An honest display degrades gracefully; a dishonest one fails silently.

C is the correct engineering fix for the polling (with scan classes, it is even better than 10 s — page 5) and it would have removed the alarm flood. It would not, by itself, have stopped the overflow, because a 10 s scan still goes blind in the rain.

A misdiagnoses the constraint. The budget that was exceeded is latency × transaction count, not bandwidth. A faster plan buys megabits the system never needed and shaves little off the round trip.

D protects against server failure, which is not what happened. Redundancy applied to the wrong layer is expensive comfort — the field link was the single point of failure, and that is fixed with RTU autonomy and store-and-forward (pages 8 and 12).

What SCADA Actually Is

Supervisory Control And Data Acquisition — four words, and every one of them is a design constraint.

machine level SCADA — distributed DCS — concentrated
THE FOUR WORDS, TAKEN SERIOUSLY CORE

Supervisory

not direct

SCADA does not close fast loops. Regulation lives in the PLC or RTU; SCADA supervises — setpoints, start/stop, modes. If the link dies, control must continue locally.

Control

write path

It can write, and that is why it is a safety and security concern. Every command needs authority, confirmation, logging and a defined behaviour when comms fail mid-command.

And Data

the real job

In practice 90 % of the value is data: what happened, when, in what order, and what it cost. That is the historian (page 8), not the screen.

Acquisition

the hard part

Getting values from remote hardware over an imperfect link, with a timestamp and a quality flag you can defend. Everything in this module descends from that sentence.

The definition worth memorising: a SCADA system is a supervisory layer that acquires time-stamped data from geographically distributed controllers over links that are assumed to be unreliable, presents it to operators, stores it, and issues supervisory commands — while the controlled process remains capable of running without it. That last clause is the test. If your process stops when the SCADA server reboots, you have not built a SCADA system; you have built a very expensive single point of failure.

The boundaries are blurring, and you should say so in an exam. Modern SCADA platforms offer redundancy and alarm management that would have been DCS-only in 1995; modern DCS platforms poll remote sites over OPC UA. The useful distinction is no longer the software — it is the assumption about the network and where the engineering database lives. Ask those two questions of any system and you will classify it correctly regardless of the badge on the cabinet. See A61 for the DCS side in depth.

The professional habit is to design this path backwards. Then specify each hop to preserve exactly that. Designed forwards, from whatever the field happens to offer, you end up with 4140 tags at one second and no way to tell live from stale.

⚡ PREDICT FIRST

A client insists on a 1 s scan for all 4140 tags across 18 cellular sites. What is the professional answer?

B. “One second” is almost never a process requirement — it is a comfort request, and it is usually wrong in both directions. A reservoir with a thirty-minute time constant does not need one-second level data; a pump-discharge pressure transient that trips a check valve needs faster than one second and will never be seen by any polled telemetry system. The right question is always “what decision does this number support, and how quickly does that decision have to be made?” The answer becomes three or four scan classes (page 5) and a specification that is both achievable and more useful than the one requested.

A buys the wrong resource — latency, not bandwidth, is the binding constraint (page 4’s budget equation).

C is the industry’s favourite mistake: it makes the alarms stop without making the data fresh, so the screens now lie quietly. It is the exact mechanism that produced the overflow on page 1.

D is unnecessary and unprofessional. The project is entirely feasible; only that one number is not. Bring the arithmetic, propose classes, and you will usually leave the meeting with a better specification than you walked into.

    Exception reporting needs a deadband, and the deadband is a design decision. Too tight and the link floods on noise; too loose and you lose the shape of the signal forever, because what was never sent cannot be recovered. Start at roughly the instrument’s own uncertainty (A11) and tune from recorded data.
  • 2

  • 3

  • 4

NAMING — THE DECISION YOU CANNOT UNDO CHEAPLY CORE
A tag name should be READABLE, SORTABLE and STABLE. A common structure: <SITE> _ <AREA/UNIT> _ <EQUIPMENT> _ <FUNCTION> _ <ATTRIBUTE> KTG_WTP_PMP01_RUN KTG_WTP_PMP01_HRS KTG_WTP_PMP01_CUR KTG_RES02_LVL_PV KTG_WTP_FIT01_FLOW_PV KTG_RES02_LVL_HI_ALM · Use the SAME equipment tag as the P&ID and the maintenance system. A tag that matches the asset register makes reliability analysis possible; one that does not makes it a manual mapping exercise forever. · Fixed-width fields sort correctly: PMP01 not PMP1, so PMP10 lands after PMP09 rather than after PMP1. · Never encode anything VOLATILE: not the PLC address, not the channel number, not the contractor's job number, not the year. · Never encode UNITS OR SCALING in the name (LVL_M then rescaled to feet is a permanent lie). · Structured tags / UDTs: define PUMP once with .RUN .TRIP .HRS .CUR and instantiate it 40 times. Consistency for free, and displays become templates. · Budget 1 hour per 100 tags for a proper database, and accept it: this is the cheapest hour you will ever spend on the project.

Why this is not pedantry. On a mature system the tag database is queried by the historian, the reports, the alarm rationalisation spreadsheet, the MES interface and eventually a machine-learning model that nobody has thought of yet. Every one of those uses assumes the names mean something consistent. A database where P1_LVL, Level_Res2 and TANK02LEVEL coexist cannot be queried programmatically, so every future integration becomes a manual mapping job — charged at consultant rates, forever.

    Derive the class from the process, not the wish. A useful rule: sample at least 5 to 10 times faster than the process time constant you need to see, and at least twice as fast as the fastest decision you must support. Page 7 makes this quantitative.
  • 2
    Three or four classes are enough. Typical: 1 s critical, 5–10 s important, 60 s background, plus “on change” for statuses and counters. More classes buy nothing and make the system harder to reason about.

THE GATEWAY QUESTION RESEARCH

Modern practice increasingly puts an edge gateway at each site rather than exposing the RTU directly: it converts the local protocol to MQTT/Sparkplug or OPC UA, buffers on disk, encrypts outbound, and often runs local logic and dashboards. It solves several problems at once — store-and-forward, firewall direction, protocol modernisation without replacing controllers — and it introduces a new one: another computer to patch, secure and maintain, at a site you visit twice a year.

The honest position: gateways are excellent where they replace a fragile inbound-polling design or enable analytics, and they are a liability where they are added to a working system for fashion. Whichever you choose, the site must still run without it. See A36 for gateway hardware and A54 for the security architecture.

Data Quality, Timestamps & Time Itself

A value without a timestamp and a quality flag is a rumour. Most SCADA disputes are really arguments about whose clock was right.

QUALITY IS A FIRST-CLASS FIELD, NOT AN AFTERTHOUGHT CORE

Every mature data model carries quality alongside value. OPC and OPC UA define it formally; DNP3 and IEC 60870-5 carry status bits with every point; NAMUR NE 107 does the same at the instrument (A11). The three states you must always be able to distinguish:

GOOD

trust it

Acquired within its scan period, from a device that answered, with no device-reported fault. The only state a display may show as a plain number.

UNCERTAIN

be careful

Last known value, substituted value, out-of-range, sensor in maintenance, or older than its scan class allows. Must look different on screen.

BAD

do not use

Comms failed, device faulted, configuration error. The display must say so — not blank, not zero, and never the last good number in the same font.

THE THREE SINS OF QUALITY HANDLING, IN ORDER OF DAMAGE 1. SUBSTITUTING ZERO for a failed value. A flow of 0 m³/h is a fact. A flow of “I do not know” is a different fact. Totalise them together and your daily report is fiction. 2. HOLDING THE LAST GOOD VALUE and drawing it normally. This is the page-1 overflow. The number is plausible, stable, and wrong. 3. Letting BAD data drive ALARMS AND LOGIC. A comms failure that trips a level alarm produces a flood, teaches operators to ignore alarms, and hides the real event (page 11). THE RULE: bad quality must PROPAGATE. If an input is bad, every calculation, alarm, total and display derived from it must inherit that badness — visibly. Most platforms support this; most projects never switch it on.
WHOSE CLOCK? SOURCE VERSUS RECEIPT TIMESTAMPS CORE
TWO TIMESTAMPS EXIST, AND THEY ARE NOT THE SAME: tsource — when the RTU/PLC observed the value or the event treceipt — when the SCADA server put it in the database On a healthy fibre link they differ by milliseconds. On a cellular link in the rain they differ by half a minute. After a two-hour outage with store-and-forward, they differ by two hours — and a system that records only treceipt will show two hours of nothing, then a vertical cliff of values all stamped at the same instant. WHY IT MATTERS BEYOND TIDINESS — SEQUENCE OF EVENTS: “Did the pump trip because the level switch operated, or did the level switch operate because the pump tripped?” That question is answered only by source timestamps of adequate resolution. Utility practice: 1 ms resolution for SOE points, RTU clocks synchronised by NTP (10–50 ms typical) or GPS/PTP (sub-microsecond) where protection or fault analysis demands it. Two events 200 ms apart, timestamped on receipt over a link with 300 ms of jitter, can be recorded IN THE WRONG ORDER. No amount of later analysis recovers the truth — and post-incident reports get written from it anyway.

    Use UTC internally, display local. Sri Lanka has no daylight saving now, but historians outlive policy, and multi-site systems cross time zones. Storing local time is a decision you will regret exactly once, in a very long meeting.
  • 3
    Check the RTU clock drift. A cheap RTC drifts seconds per day. If it timestamps at source and never synchronises, its history slowly detaches from everyone else’s — and store-and-forward faithfully preserves the error.
  • 4
    Log the data age on screen. “Updated 3 s ago” costs one label and removes an entire class of operator error. It is the cheapest safety feature in this module.

WHY A TIME-SERIES DATABASE, NOT A RELATIONAL ONE CORE

A historian is a database specialised for one shape of data: tag, timestamp, value, quality, written constantly and read in ranges. That specialisation buys enormous advantages, and it is why the industry uses PI, Wonderware Historian, Canary, InfluxDB, TimescaleDB or Aveva/Ignition historians rather than a plain SQL table.

  • 1
    Append-only, time-ordered writes — no random updates, so the storage engine can pack data tightly and write sequentially. This is why a historian can absorb tens of thousands of values a second on modest hardware.
  • 2
    Columnar / per-tag storage — a query for one tag over one month reads a contiguous block instead of scanning rows for every other tag.
  • 3
    Native compression (deadband + swinging door + delta-of-delta timestamp encoding), typically 5:1 to 20:1 on real process data with no loss of usable shape.
  • 4
    Interpolation and aggregation as first-class queries — hourly averages, time-weighted totals, minimum and maximum per interval, all computed correctly across irregular samples. Doing that in SQL over compressed data is where hand-built systems die.
  • 5
    Time-weighted arithmetic matters. The average of stored points is not the average of the signal when samples are irregular — you must weight each value by how long it applied. Every serious historian does this; every spreadsheet export forgets it, which is why report numbers argue with trend screens.
STORAGE ARITHMETIC, AND WHAT COMPRESSION REALLY COSTS CORE
RAW RATE bytes/s = Ntags × (bytes per sample) / (scan interval) Cold open, uncompressed, 8 bytes per sample (value + time + quality): 4140 × 8 / 1 s = 33.1 kB/s = 2.86 GB/day = 1.04 TB/year Honestly classified (page 5, ~300 tag-reads/s): 300 × 8 = 2.4 kB/s = 207 MB/day = 76 GB/year Plus swinging-door compression at a typical 90 %: → ~7.6 GB/year for the whole scheme TWO SETTINGS DO ALL THE WORK — AND BOTH ARE IRREVERSIBLE: · EXCEPTION deadband: what the acquisition layer bothers to pass on · COMPRESSION deviation: what the historian bothers to keep Rule of thumb: set exception ≈ instrument noise, and compression deviation ≈ the smallest change you would ever need to SEE on a trend (often 0.5–1 % of span for analogue process values). What you discard, you discard forever. Disk is cheap; the incident three years from now that needs the missing detail is not. When in doubt, compress less on anything involved in safety, energy or quality disputes.

SITUATION AWARENESS — WHAT A DISPLAY IS FOR CORE

Endsley’s model of situation awareness has three levels, and a display can support or sabotage each of them. This is the framework behind ISA-101 and the High-Performance HMI literature (Hollifield, Habibi, Nimmo), and it is the vocabulary to use when you argue for a display standard.

Level 1 — Perception

what is

Can the operator see the state? Supported by legible type, adequate contrast, consistent placement. Sabotaged by clutter and by colour used for everything.

Level 2 — Comprehension

so what

Does the operator know whether it is normal? Supported by analogue indicators showing the value against its limits, and by embedded trends.

Level 3 — Projection

what next

Can they see where it is heading? Supported by trends, rate-of-change and predicted-time-to-limit. This is the level a digital number alone can never reach.

The test that settles most design arguments: show the display to an experienced operator for five seconds, take it away, and ask — is anything abnormal, where, and is it getting worse? A high-performance display passes. A colourful P&ID mimic almost never does, because the reader has to inspect every number in turn to find out whether it is in range. That difference is worth minutes in an upset, and minutes are what upsets are made of.

The philosophy belongs to A53. What belongs here is the part SCADA uniquely gets wrong: alarms produced by the telemetry rather than by the plant.

THE THREE RULES, STATED ONCE CORE
From ISA-18.2 / IEC 62682, the minimum any SCADA engineer must know: 1. AN ALARM REQUIRES AN OPERATOR RESPONSE. If there is nothing for a human to do, it is an EVENT for the log, not an alarm on the screen. 2. TARGET RATES, per operator: ~150/day (≈6/hour) very likely acceptable ~300/day (≈12/hour) maximum manageable FLOOD = more than 10 alarms in any 10-minute window. 3. PRIORITY MUST BE RATIONED. Roughly 5 % high, 15 % medium, 80 % low, and three priorities is usually enough. If everything is high, nothing is. Two of everything is easy to buy and hard to earn. The number that decides your uptime is almost never the component failure rate.

AVAILABILITY ARITHMETIC, WITH THE TERM THAT MATTERS CORE
SINGLE COMPONENT A = MTBF/(MTBF + MTTR) U = 1 − A MTBF 20 000 h, MTTR 8 h → U = 8/20 008 = 4.00e−4 A = 99.96 %, downtime 3.5 h/year TWO IN PARALLEL, IF THEY WERE TRULY INDEPENDENT U = (4.00e−4)² = 1.60e−7 → downtime 0.0014 h/year (5 seconds) — a number no real system has ever achieved. TWO IN PARALLEL, WITH COMMON CAUSE (β = 5 %) U = β·(1−A) + (1−β)·(1−A)² = 0.05 × 4.00e−4 + 0.95 × 1.60e−7 = 2.00e−5 + 1.52e−7 = 2.02e−5 → A = 99.998 %, downtime 0.18 h/year ≈ 11 minutes The common-cause term is 125× larger than the redundancy term. Security Essentials for SCADA

The full method is A54. What belongs here is what makes SCADA different: unmanned sites, public networks and a write path to real valves.

WHY SCADA IS THE EXPOSED LAYER CORE

A SCADA system sits at Purdue Level 2 and, by its nature, talks in both directions: down to controllers that move things, and up through a DMZ to reporting and business systems. Add geography — dozens of unmanned sites on public cellular networks — and you have the most attackable topology in industrial automation. Four properties make it distinct from a DCS:

Public transport

cellular

Traffic crosses infrastructure you do not own. Encryption and authentication are not optional extras; an APN is not a security boundary by itself.

Unmanned sites

physical

A cabinet in a field with a padlock. Physical access defeats most network controls, so assume a site can be compromised and design so that one site cannot command another.

A real write path

control

Supervisory commands start pumps and open valves. Authority, confirmation, logging and rate limiting are safety features, not IT policy.

Remote support

access

Vendors and integrators need in. Unmanaged remote access is the most common real-world entry point — and the hardest to remove once operations depend on it.

THE TEN THINGS THAT ACTUALLY GET DONE — AND MOSTLY ARE NOT CORE
  • 1
    Change every default credential, on RTUs, radios, modems, switches, HMI panels and the historian. Keep them in a managed password store, not in a spreadsheet called passwords.xlsx.
  • 2
    Prefer outbound-only connections from site to centre — MQTT/Sparkplug or OPC UA reverse-connect — so no site needs an inbound port open on a public network. This is the single largest architectural improvement available (page 6).
  • 3
    Segment by consequence, not by convenience (zones and conduits, IEC 62443). Sites must not be able to reach each other; the business network must not be able to reach Level 2 directly; the historian belongs in the DMZ where reporting users can read it.
  • 4
    Authenticate and authorise every write. Named accounts, no shared operator login for commands, role-based rights, and every command logged with who, what, when and from where. That log is also your operational record when something goes wrong.
  • 5
    Managed remote access: broker or jump host, multi-factor authentication, time-limited sessions, session recording, and an operator-side enable so field staff know when a vendor is connected.
  • 6
    Patch on a schedule you control, tested on a spare or virtual machine first. OT patching is slower than IT patching for good reasons; the answer is a documented cycle with compensating controls, not indefinite postponement.
  • 7
    Backups that have been restored. Servers, tag database, displays, RTU and PLC programs, radio and modem configurations, licences. Offline copy, tested annually. An untested backup is a rumour.
  • 8
    No engineering software on the operator console, no email or browsing on any OT machine, USB ports controlled, and removable media scanned on a standalone kiosk.
  • 9
    Monitor for the boring things: unexpected new devices, failed logins, configuration changes, and the appearance of protocols that should not exist on that network. Passive monitoring first (A54).
  • 10
    Write the incident plan before you need it, and include the question that only engineers can answer: under what circumstances do we disconnect or shut down? That is a safety and operations decision, never an IT one.

This is why OT security measures must be judged by what they do to availability first — and why “just push the patch” is the wrong instinct in a control room. Recap, Failure Modes & Quiz

Eight ideas that carry the module, six ways real SCADA systems fail, and six questions that test whether the ideas transferred.

THE EIGHT IDEAS CORE
  • 1
    SCADA assumes the link will fail. That single assumption produces every other design rule: local autonomy, store-and-forward, quality flags, honest displays.
  • 2
    The poll budget is latency × transaction count, not bandwidth. Write it down before promising a scan rate.
  • 3
    Scan classes are the biggest performance lever you have. Honest classification cut the cold open’s load by a factor of 14 and made it more responsive where it mattered.
  • 4
    A value without a timestamp and a quality flag is a rumour. Timestamp at source, propagate bad quality, and never substitute zero.
  • 5
    The tag database outlives everything. Name it as though the next engineer is a stranger with a query tool, because they are.
  • 6
    The historian is the asset. Compression settings are irreversible; retention and backups are business decisions, not IT housekeeping.
  • 7
    A display is an instrument for situation awareness. Grey background, colour reserved for abnormal, analogue indicators with limits, embedded trends — and it must be able to say “I do not know”.
  • 8
    Availability is decided by common cause. Redundancy is cheap; independence is what you are buying. And the RTU’s autonomy protects the process, while everything upstream only protects the view.
SIX WAYS REAL SCADA SYSTEMS FAIL
1 · A scan rate that was never possible
Everything in one class at one rate, polled sequentially over a high-latency link. Fingerprint: cycle time far longer than specified, comms alarms in bursts, worse in bad weather. Prevention: the poll budget of page 4 before the specification is signed, then three or four honest scan classes.
2 · A display that cannot say “I do not know”
Stale values drawn exactly like live ones; zeros substituted for failures. Fingerprint: operators making confident decisions from old data — and a post-incident report that blames them. Prevention: quality propagation, greyed or hatched stale values, data age on screen.
3 · A system that alarms about itself
Per-tag comms alarms, a one-poll watchdog, and process alarms evaluated on bad data. Fingerprint: thousands of alarms a day, most of them communications. Prevention: one alarm per site, k consecutive failures, quality gating (page 11).
4 · No autonomy at the remote site
Logic that lives in the master, so the process stops when the link does. Fingerprint: “we had to run it manually by telephone”. Prevention: all regulation and interlocking in the RTU or PLC; SCADA supervises only. Test it by unplugging the link on purpose.
5 · A historian nobody can use
Inconsistent names, aggressive compression, missing metadata, no tested backup. Fingerprint: every analysis question becomes a two-week manual exercise; a disk failure loses years. Prevention: naming standard, defensible compression, metadata with every backup, restore tested annually.
6 · Redundancy with a shared dependency
Two servers on one host, two paths on one mast, two power supplies on one board. Fingerprint: both halves fail together, and the failover was never tested under load. Prevention: draw the dependency diagram, hunt for anything that appears once, and test failover quarterly with operators present.
✓ QUICK CHECK — SIX QUESTIONS

Q1: A client specifies a 1 s scan for 25 sites, each needing 4 Modbus transactions, over links with a 250 ms round trip. Is it achievable, and what do you propose?

Tap to reveal ↓A: Sequentially, no. 25 × 4 = 100 transactions × (250 + 30) ms = 28 s per cycle — 28 times the specification.

Proposal, in order: (1) split the tags into three scan classes so only the genuinely critical points are on 1 s — typically about 2 % of them, one transaction per site; (2) use concurrent channels: with 8 channels the critical class becomes about 3 sites × 1 transaction × 0.28 s ≈ 0.84 s, which meets the requirement for what matters; (3) move statuses and events to exception reporting (DNP3 unsolicited or IEC 60870-5-104 spontaneous) so changes arrive immediately rather than waiting for a poll; (4) add store-and-forward so outages produce history rather than holes. Then write the achieved figures into the FDS as testable numbers.

Q2: Why is substituting zero for a failed analogue value worse than showing nothing at all?

Tap to reveal ↓A: Because zero is a valid process value, so it is indistinguishable from a fact. A flow of 0 m³/h means “no flow”; a failed measurement means “unknown”. Substituting one for the other corrupts three things at once: the operator’s judgement, the alarms (a zero flow may trigger a low-flow alarm that has nothing to do with the process), and the totals and reports, which now integrate fiction. Correct behaviour: mark the tag BAD, propagate that to every derived value and alarm, show it visibly on the display, and exclude it from totalisation with the gap recorded.

Q3: Two events happen 200 ms apart at a remote site. The link has 300 ms of jitter and the SCADA timestamps on receipt. What can you conclude about their order?

Tap to reveal ↓A: Nothing. With 300 ms of jitter and events 200 ms apart, the recorded order can easily be reversed, and there is no way to detect that it has been. Any causal conclusion — “the level switch caused the trip” — is unsupported.

The fix is architectural, not analytical: timestamp at the source in the RTU, with a synchronised clock (NTP for 10–50 ms, GPS/PTP for sub-millisecond), buffer events locally, and transmit them with their source times. Sequence-of-events points in utility practice are timestamped to 1 ms for exactly this reason. Note also the corollary: if your system only has receipt timestamps, do not write causal statements into incident reports from it.

Q4: A pair of redundant servers each have MTBF 20 000 h and MTTR 8 h. Why is the achieved availability nowhere near the 99.99999 % the parallel formula predicts?

Tap to reveal ↓A: Because the parallel formula assumes independence, and no real pair is independent. With β = 5 % common cause:
U = β(1−A) + (1−β)(1−A)² = 0.05(4.0×10⁻⁴) + 0.95(1.6×10⁻⁷) = 2.02×10⁻⁵
→ about 11 minutes a year, not 5 seconds — and the common-cause term is 130× the redundancy term.

What they share is the answer: the same room, UPS, switch, virtualisation host, firmware version, patch window and engineer. Money spent reducing β — separate power, separate host, staggered patching, tested procedures — buys far more availability than a third server.

Q5: Why does a high-performance HMI use a grey background and almost no colour?

Tap to reveal ↓A: Because colour is the strongest pre-attentive visual cue available, and it only works if it is scarce. On a display where every pipe, tank and value is saturated colour, an abnormal condition has no way to stand out — the operator must read every element in turn to find out whether anything is wrong, which is slow and error-prone under stress. A low-contrast grey background with greyscale normal states leaves the whole colour range free to mean “attend to this”.

Two supporting reasons worth the extra marks: eye strain over a 12-hour shift (large type, moderate contrast, no glare) and accessibility — roughly 8 % of men have a colour-vision deficiency, so colour must never be the only carrier of meaning. The test: five seconds of viewing should answer “is anything abnormal, where, and is it getting worse?”

Q6: A regional scheme has 4000 alarms a day, 3400 of them communications-related, and management asks for “an alarm management project”. What do you do in the first week, and what do you refuse?

Tap to reveal ↓A: First week — configuration, not project. (1) Replace per-tag comms alarms with one alarm per site, with all its tags going BAD quality silently. (2) Require k consecutive failed polls before alarming: at 2 % loss and a 2 s poll, k = 3 takes nuisance alarms from ~864/day to ~0.35/day for six seconds of detection delay. (3) Gate process alarms on quality so bad data cannot raise level, flow or pump alarms. (4) Route store-and-forward replays to the log and historian, not the live alarm queue. Then measure for a week and publish the before/after rate.

Then the real project: rationalise the remaining ~600 process alarms against a written philosophy, with priorities rationed, per A53.

What I would refuse: to lengthen the watchdog timeout until the alarms stop without fixing the mechanism — that leaves the screens showing stale numbers quietly, which is precisely how the reservoir on page 1 overflowed. I would also refuse to switch comms alarms off entirely: losing a site for an hour is a genuine operational event and somebody must own the response.

Worked Examples

Five complete problems of the kind that arrive as a tender document. Method first, arithmetic second, and always what the number means.

WE1 · POLL BUDGET AND SCAN-CLASS DESIGN FOR 25 SITES CORE

A water authority tenders a scheme: 25 remote sites, 180 tags each (120 analogue, 60 digital), Modbus TCP over cellular, measured RTT 250 ms (median) and device response 30 ms. The specification says “2 second scan, all tags”. Assess it and propose a design.

STEP 1 — TRANSACTION COUNT analogue: 120 registers → 1 block (125 max) digital: 60 bits → 1 block → 2 transactions per site, ttransaction = 0.250 + 0.030 = 0.28 s STEP 2 — SEQUENTIAL CYCLE (as most systems are configured by default) 25 × 2 × 0.28 = 14.0 s against a 2 s specification — 7× over STEP 3 — WHAT CONCURRENCY BUYS 8 channels → ⌈25/8⌉ = 4 sites worst case → 4 × 2 × 0.28 = 2.24 s (just fails) 10 channels → 3 sites → 3 × 2 × 0.28 = 1.68 s ✓ STEP 4 — THE DESIGN THAT ACTUALLY WINS: HONEST CLASSES critical 2 % = 90 tags (~4/site, 1 transaction) at 2 s important 20 % = 900 tags (~36/site, 1 transaction) at 10 s background 78 % = 3510 tags (~140/site, 2 transactions) at 60 s critical cycle at 8 channels: 4 × 1 × 0.28 = 1.12 s ✓ comfortably LOAD COMPARISON (tag-reads per second): naive: 4500/2 = 2250/s classified: 90/2 + 900/10 + 3510/60 = 45 + 90 + 58.5 = 193.5/s → 11.6× less load, and the tags that matter are FASTER than specified Link traffic: ~15.8 transactions/s × ~350 B ≈ 5.5 kB/s ≈ 44 kbps — which is why “we need a bigger data plan” was never the answer.

What to write in the tender response. Not “2 seconds is impossible” — that loses the job. Write: “A 2 s update is provided for the 90 tags that drive operator action within seconds, with 10 s and 60 s classes for the remainder, plus exception reporting on all statuses. This meets the intent of the specification, is achievable on the measured link, and leaves headroom for the four sites planned in phase 2.” Then attach this arithmetic as an appendix. It is the difference between a proposal and a promise.

WE2 · HISTORIAN SIZING, AND WHERE NOT TO COMPRESS CORE

The same scheme. 8 bytes per stored sample. Compare naive and classified acquisition, apply realistic compression, and decide the retention. One flow meter is used for a regulatory return.

RAW STORAGE RATE = (samples/s) × (bytes/sample) NAIVE, all 4500 tags at 2 s = 2250 samples/s: 2250 × 8 = 18 000 B/s → 1.56 GB/day → 568 GB/year five years online = 2.8 TB CLASSIFIED, 193.5 samples/s: 193.5 × 8 = 1548 B/s → 134 MB/day → 48.8 GB/year PLUS swinging-door compression at a realistic 85 %: → 7.3 GB/year five years online = 36.6 GB — a rounding error on any modern disk TOTAL REDUCTION: 11.6× from classification × 6.7× from compression = 78× THE EXCEPTION THAT EARNS THE MARKS: The regulatory flow meter must NOT be compressed aggressively. Store it at full scan resolution, with a tight deviation, retained for the full statutory period, and EXCLUDE it from the tiered-aggregation policy. Cost of that decision: one tag at 10 s for 7 years = 8.64 × 10⁵ samples/day × 8 B ≈ 0.25 GB/year. Negligible. The general rule: compress for convenience, but never compress anything that may be produced as evidence. Identify those tags at design time and mark them in the tag database, because nobody will remember in year four.

Retention design for this scheme: full resolution online 2 years; hourly time-weighted aggregates retained for the life of the asset; regulatory tags at full resolution for the statutory period; nightly backup off the machine with the tag metadata exported alongside; one restore test a year, recorded. That paragraph is worth more at handover than any screen in the system.

The contract requires 99.9 % availability of the operator view per site (≤ 8.76 h/year). Components: redundant servers (MTBF 20 000 h, MTTR 8 h, β = 5 %), redundant switches (MTBF 100 000 h, MTTR 4 h, β = 10 %), and a single cellular link with a measured availability of 99.5 %. Does it pass?

WE4 · WATCHDOG AND ALARM LOAD FOR THE WHOLE SCHEME CORE

25 sites, 2 s critical poll, measured packet loss 2 %. Process alarms are expected to run at about 120 per day for the whole scheme. Choose k so the console stays inside ISA-18.2 guidance, and state the cost.

Problem Set — 90 Marks

Ten problems under exam conditions. Work each on paper before revealing; method carries the marks.

P1  [6 marks] · POLL BUDGET

40 remote sites, 3 transactions each, RTT 400 ms, device response 25 ms. Find the sequential cycle time, and the cycle time with 12 concurrent channels. Comment on a 5 s specification.

Tap to reveal ↓ttransaction = 0.400 + 0.025 = 0.425 s
Sequential: 40 × 3 × 0.425 = 51.0 s
With 12 channels: ⌈40/12⌉ = 4 sites worst case → 4 × 3 × 0.425 = 5.1 s

Comment: 5 s is just missed, with no margin for a link that degrades — and at 400 ms this is a satellite-like or heavily congested path, so degradation is likely. Options, in order of preference: (1) scan classes, so the 5 s requirement applies only to the small critical set (one transaction per site → 1.7 s); (2) more channels if the master genuinely supports them; (3) exception reporting for statuses; (4) renegotiate the number, with this arithmetic attached. Do not simply lengthen the watchdog.
P2  [8 marks] · DESIGN THE SCAN CLASSES

A system has 6000 tags. Testing shows the acquisition layer sustains about 250 tag-reads per second before the cycle starts slipping. Design a scan-class scheme with margin, and state the assumptions.

Tap to reveal ↓First attempt (the usual 2/20/78 split): 120 at 1 s = 120/s; 1080 at 10 s = 108/s; 4800 at 60 s = 80/s → total 308/s — over budget.

Revised, with the reasoning:
critical 1 % = 60 tags at 1 s → 60/s
important 15 % = 900 tags at 10 s → 90/s
background 84 % = 5040 tags at 120 s → 42/s
Total 192/s — 77 % of the 250/s budget, leaving ~23 % margin.

Assumptions to state: that the critical set really is 60 tags (it must be justified tag by tag, not assumed); that statuses and alarms are event-driven rather than counted in these classes; that derived/calculation tags are included in the load; that 250/s was measured on the real link and not taken from a datasheet; and that margin is reserved for future sites, not consumed at commissioning.

Mark-earning observation: background at 120 s is perfectly adequate for temperatures, totals and statuses, and it is the single change that buys the margin. Slow is not the same as neglected.
P3  [10 marks] · HISTORIAN SIZING

Using the P2 design (192 samples/s), 12 bytes per stored sample, compression 88 %, retention 7 years online. Compute daily and annual storage, the 7-year total, and state two design decisions that follow.

Tap to reveal ↓Raw rate = 192 × 12 = 2304 B/s
Per day = 2304 × 86 400 = 1.99×10⁸ B = 199 MB/day
Per year = 72.7 GB/year raw
With 88 % compression: 72.7 × 0.12 = 8.7 GB/year
Seven years = 61 GB

Two decisions that follow:
1. Storage is not the constraint — 61 GB is trivial, so there is no engineering reason to compress harder than the data justifies. Set the deviation from what you need to see (typically 0.5–1 % of span), not from a disk budget.
2. Backup and restore, not disk size, is the real problem. 61 GB must be backed up off the machine, with the tag metadata, and restored as a test at least annually. Also define tiered aggregation now (full resolution 2 years, hourly time-weighted aggregates for life) and identify any regulatory tags that are excluded from compression and aggregation.

Common error: multiplying total tags by the fastest scan rate. Storage follows the actual acquisition rate, which is what the scan classes determine — here 192/s, not 6000/s.
P4  [8 marks] · WHAT CAN YOU PROVE ABOUT ORDER?

A post-incident report states: “the low-level switch operated at 02:14:07.4, the pump tripped at 02:14:07.6, therefore the low-level switch caused the trip.” The site reports over cellular with receipt timestamping; measured RTT is 180 ms median, 700 ms at the 95th percentile. Assess the claim.

Tap to reveal ↓The claim is unsupported. The two events are 200 ms apart in receipt time, while the link’s own variability spans 180–700 ms. Two messages sent in one order can easily arrive in the other, and nothing in the record allows you to tell. The 0.1 s resolution of the printed times gives an illusion of precision that the transport does not support.

What can honestly be said: both events occurred within roughly one second of each other, in an order that is not established.

What to change, in order: (1) timestamp at source in the RTU for all SOE points, at 1 ms resolution; (2) synchronise the RTU clock — NTP for 10–50 ms, GPS/PTP where protection analysis is needed — and record the achieved accuracy; (3) buffer events locally and transmit with source times, so an outage does not destroy the sequence; (4) if causality genuinely matters for this trip, take the evidence from the RTU or PLC event log, not from the SCADA receipt log.

The professional habit worth a mark: when a report needs event order, first ask whose clock produced these timestamps. If the answer is “the server, on receipt”, write that limitation into the report rather than reasoning past it.
P5  [10 marks] · AVAILABILITY, AND WHERE TO SPEND

Server pair: MTBF 30 000 h, MTTR 12 h, β = 8 %. Single comms link availability 99.2 %. (a) Site view availability and annual downtime. (b) Which term dominates. (c) Effect of adding a second, independent link at 98.5 % with β = 3 %.

Tap to reveal ↓(a) Server single: U = 12/30 012 = 4.00×10⁻⁴
Server pair: U = 0.08(4.00e−4) + 0.92(4.00e−4)² = 3.20e−5 + 1.47e−7 = 3.21e−5
Comms: U = 1 − 0.992 = 8.00e−3
Series total: U ≈ 8.03e−3 → A = 99.20 % → downtime = 8760 × 8.03e−3 = 70.4 h/year

(b) The comms link is 99.6 % of the unavailability (8.00e−3 of 8.03e−3). The redundant server pair contributes almost nothing — and note that within the pair the common-cause term (3.20e−5) is 218× the independent-failure term (1.47e−7).

(c) Dual path: U = 0.03(8.00e−3) + 0.97(8.00e−3 × 1.50e−2) = 2.40e−4 + 1.16e−4 = 3.56e−4
New total: 3.56e−4 + 3.21e−5 = 3.89e−4 → A = 99.96 % → 3.4 h/year — a 20.7× improvement.

The engineering conclusion: spend on the second path first, then on reducing β (separate mast, separate power, separate provider, staggered patching). A third server would change the answer in the fourth decimal place.
P6  [8 marks] · WATCHDOG DESIGN AT HIGH LOSS

30 sites, 5 s poll, measured packet loss 5 %. Find the smallest k that keeps nuisance comms alarms below one per day for the whole system, state the detection delay, and comment.

Tap to reveal ↓Polls per site per day = 86 400/5 = 17 280; system total = 30 × 17 280 = 518 400 polls/day.
Nuisance alarms/day ≈ 518 400 × 0.05k:
k = 1 → 25 920  k = 2 → 1296  k = 3 → 64.8  k = 4 → 3.24  k = 5 → 0.16 ✓
k = 5, giving a detection delay of 5 × 5 = 25 s.

Comment — this is where the marks are. Needing k = 5 is a diagnosis, not a design: 5 % loss is a broken link, not a normal one. The right response is to fix the radio path (alignment, obstruction, interference, power budget) or change medium, then re-tune k downwards. Accepting 25 s of blindness on every site is a poor substitute for a path survey.

Also worth stating: the formula assumes independent losses. Real radio loss is bursty, so consecutive failures are more likely than the arithmetic suggests — nuisance alarms will be somewhat worse than predicted, and a real outage will be detected about as predicted. Bursty loss makes the case for fixing the link stronger, not weaker.
P7  [10 marks] · A REPORT BUILT ON BAD DATA

A daily volume report totalises a flow tag. Average flow is 120 m³/h. For 3 hours the transmitter was in fault and the SCADA substituted zero. Compute the error, then state the correct handling.

Tap to reveal ↓Arithmetic: true total = 24 × 120 = 2880 m³. Recorded total = 21 × 120 + 3 × 0 = 2520 m³.
Error = −360 m³ = −12.5 %, and nothing in the report says so.

Correct handling, in order:
1. Do not substitute. The tag goes BAD and the totaliser must exclude the bad interval rather than integrating a fictional zero.
2. Report coverage explicitly: “2520 m³ over 21.0 h of valid data (87.5 % coverage)”. A number without its coverage is not a measurement.
3. If an estimate is required (for billing or a regulatory return), state the method and label it: pro-rata on valid hours gives 2880 m³; a better estimate may come from the pump run hours or the downstream reservoir change. Never let an estimate enter the record unlabelled.
4. Fix the propagation: quality must flow from the tag into the totaliser, the report and any KPI derived from it (page 7).
5. Log the gap in a data-quality report reviewed with the KPIs (page 14), because a plant that does not count its gaps cannot trust any of its numbers.

The wider point: a 12.5 % error in a daily volume is the kind of number that later becomes an argument with a regulator or a customer. The engineering failure was not the transmitter fault — faults are expected — it was substituting a plausible value for an unknown one.
P8  [10 marks] · DIAGNOSE FROM A SYMPTOM

Operators report that values “update in bursts about every 30 seconds”, although the scan class is configured at 5 s. Comms alarms are rare. Diagnose systematically, listing the tests in order.

Tap to reveal ↓What the symptom means. Updates arriving in bursts at a period far longer than the configured scan is the classic signature of a poll cycle that exceeds its scan interval. When that happens the configured interval becomes meaningless — the effective update rate is the cycle time, and every tag refreshes as its turn comes around.

Candidate causes, in likelihood order:
1. Cycle time > scan interval (page 4): too many transactions, too much latency, or fewer real channels than assumed. Most likely.
2. A serialised driver: the master licences many channels but the protocol driver processes one request at a time.
3. One slow or failing device holding the channel — a site that times out on every poll adds its full timeout to every cycle. A single bad site can dominate.
4. Server load: thousands of derived tags or scripts evaluating on a fast class, starving the acquisition task.
5. Client-side refresh throttling or a display bound to a slow class, if the problem is only on one screen.
6. VPN or session re-establishment adding a periodic stall.

Tests, in order: (a) read the driver’s own statistics — actual cycle time, transactions per second, timeouts per device: most platforms expose these and the answer is usually there in a minute; (b) look for one device with a much higher timeout or retry count and disable it temporarily to see whether the cycle collapses; (c) compare configured channels with the driver’s concurrency in the manual; (d) ping the worst site for an hour and take median and 95th percentile; (e) check server CPU and the count of derived tags on the fast class; (f) recompute the poll budget with the measured numbers and compare it with the observed 30 s — if they agree, the diagnosis is confirmed and the fix is scan classes plus concurrency, not a faster link.

What not to do: raise the scan rate. The system is already saturated; asking for more only lengthens the cycle.
P9  [10 marks] · SPECIFY A SCHEME

A tea estate group wants one SCADA system covering 12 sites: 4 factory utility rooms (compressed air, boilers, dryers), 5 water pumping stations, 2 mini-hydro plants and a central office. Links available: fibre at 2 factories, cellular elsewhere. Specify architecture, protocols, scan classes, redundancy, security and HMI. State three risks.

Tap to reveal ↓Architecture: Level 1 control local at every site — PLC in factories and mini-hydro, RTU at pump stations — all sites fully autonomous. Redundant SCADA server pair at the central office (Level 2), historian in a DMZ (Level 3) so office users read reports without touching Level 2. Distributed acquisition: an edge gateway at each site buffering to disk.

Protocols: outbound MQTT/Sparkplug B from each gateway to a broker at the centre — no inbound ports on cellular sites, birth/death certificates give honest state, and store-and-forward is native. Inside each site, whatever the controllers speak (Modbus TCP, or OPC UA where available). Mini-hydro protection and metering may need IEC 60870-5-104 or 61850 if the utility interface requires it.

Scan classes: critical 1–2 s (boiler and dryer interlock feedback, hydro generator status, pump run/trip, comms health); important 10 s (pressures, flows, levels, temperatures); background 60–120 s (totals, energy, diagnostics); statuses and alarms on change. Budget with page 4’s equation using measured RTT per site.

Redundancy, in value order: site autonomy and UPS first; store-and-forward second; second comms path for the two mini-hydro sites and any pump station whose failure risks supply (cellular + radio, different provider and mast); server pair with tested quarterly failover; dual switches; documented remote access for out-of-hours support.

Security: outbound-only connections, per-site credentials changed from default, zones so no site can reach another, named accounts with role-based write rights, all commands logged, managed remote access with MFA and session recording, tested backups of every gateway/PLC/RTU program, and surge protection plus proper earthing at every antenna (lightning is the dominant physical threat here).

HMI: high-performance style — one Level 1 overview of all 12 sites with comms health and key states; Level 2 per site; Level 3 per equipment; grey background, colour for abnormal only, analogue indicators with limits, embedded trends, data age shown. One alarm per site for comms, k = 3, process alarms gated on quality.

Three risks: (1) cellular coverage and latency at estate elevations — survey before designing the poll, and budget for a radio fallback; (2) lightning — a seasonal RTU-and-modem replacement cycle unless surge protection and earthing are engineered and inspected; (3) ownership after handover — twelve sites and no named engineer produces an orphan system in two years, so specify training, documentation, backups and a quarterly KPI review as deliverables.
P10  [12 marks] · SYNTHESIS — AND A REFUSAL

The page-1 water scheme has been fixed: scan classes, k = 3, quality on the displays, store-and-forward. Management now asks for (a) a cloud dashboard so the general manager can watch the scheme on a phone, (b) a new pumping station added next month, and (c) “alerts by WhatsApp instead of the control room, so we can reduce night staffing”. Respond as the engineer.

Tap to reveal ↓(a) The cloud dashboard: yes, with a specific architecture. Push data outward from the historian or an edge broker — MQTT/Sparkplug or an HTTPS publish — into a read-only cloud dashboard. Nothing in the cloud may reach into Level 2, and it must carry no write path. Include the comms-health strip and data age on the mobile view, or the general manager will make the page-1 mistake on a smaller screen. Budget for the licence, the data plan and, importantly, someone to maintain it.

(b) The new pumping station: yes, and it is a change, not an addition. Recompute the poll budget with 19 sites (page 4); confirm the critical class still meets its interval and that the margin reserved at design time covers it. Add the tags using the existing naming standard and templates; extend the Level 1 overview; rationalise its alarms; add it to the backup, the KPI report and the O&M documentation; and run the page-16 link-failure acceptance test on it before handover. (c) The staffing proposal: this is where I refuse, and the refusal must be specific. Notification to a phone is a convenience, not an alarm system: message delivery is not guaranteed, not acknowledged, not logged, not escalated, and depends on the same public network that fails in the weather — which is precisely when the alarms matter. Removing the night operator also removes the layer that responds, and a SCADA system with nobody to respond is a recording device.

What I would propose instead: keep the manned console as the alarm system of record; add phone notification as a secondary path for a small, explicitly rationalised set of high-priority alarms, with an acknowledgement requirement and escalation if not answered within a defined time; measure the response performance for six months; and only then discuss staffing, with evidence. If the driver is genuinely cost, the honest options are automation of the response (more RTU logic, larger buffer storage so a slow response is tolerable) or a shared on-call rota — both of which can be engineered and evidenced.

Marking: 3 for the cloud architecture with no inbound path and no write access, 4 for treating the new site as a managed change with the budget recomputed, 5 for the refusal with a technically grounded alternative.

Derivations & Traps

Four results the module leaned on, built from first principles — because a formula you can reconstruct is one you can defend in a tender meeting.

DERIVATION 1 · THE POLL-CYCLE BUDGET CORE
A poll is a request-response CONVERSATION. Its cost is dominated by the time the signal spends travelling, not by the size of the message. One transaction: t = trequest flight + tdevice + tresponse flight + tmaster = RTT + tdevice + tmaster Note what is ABSENT: message length. At 300 bytes over even a 1 Mbit/s link the serialisation time is 2.4 ms — negligible beside a 200 ms RTT. THIS is why bandwidth upgrades do not fix poll performance. Transactions needed per device, for a block-read protocol with block limit B: n = ⌈A/B⌉ + ⌈D/Bbits⌉ + (one extra per non-contiguous address range) SEQUENTIAL (one conversation at a time, the default): Tcycle = Nsites · n · t CONCURRENT on C independent channels: Tcycle = ⌈Nsites/C⌉ · n · t THE CONSEQUENCE THAT SURPRISES PEOPLE — WHAT HAPPENS WHEN YOU OVER-ASK: If you configure a scan interval Tscan < Tcycle, the system cannot obey it. The scheduler simply runs the cycle back-to-back, so: effective update interval = max(Tscan, Tcycle) and every tag refreshes when its turn arrives — which the operator sees as values updating in BURSTS at the cycle period (P8). Asking for a faster scan than the budget allows does not make the data fresher; it makes the system saturated and the timing unpredictable. Corollary, and it is the design rule of page 5: since Tcycle ∝ n, the way to a fast critical class is to make n SMALL for that class — a handful of contiguous registers per site, not the whole database.
DERIVATION 2 · HOW FAST MUST YOU SAMPLE? CORE
Take the standard first-order process response to a step: y(t) = y∞(1 − e−t/τ) Change over one sampling interval T, starting at time t: Δy = y(t+T) − y(t) = y∞ e−t/τ (1 − e−T/τ) The largest step occurs at t = 0: Δymax = y∞(1 − e−T/τ) and for T ≪ τ this is approximately Δymax ≈ y∞ · T/τ SO THE SAMPLING RULE FALLS OUT DIRECTLY: T = τ/5 → largest jump between samples = 1 − e−0.2 = 18 % of span T = τ/10 → 1 − e−0.1 = 9.5 % T = τ/20 → 4.9 % → T ≤ τ/10 reproduces the curve to about 10 % per step, which is ample for trending, alarming and operator judgement. T ≤ τ/5 is the practical minimum. Sampling at τ/1000 adds nothing except load. DETECTION DELAY FOR A THRESHOLD CROSSING: worst case = T (it crossed just after the last sample) average = T/2 plus any device filtering time constant, plus k·T if k consecutive samples are required to confirm. PERIODIC FEATURES — NYQUIST, THEN REALITY: to DETECT a periodic feature of period P: T < P/2 (Nyquist) to SEE ITS SHAPE: T ≤ P/10 Sample slower than P/2 and it does not merely vanish — it ALIASES, appearing as a slow drift that is entirely fictitious. A 4 s pressure surge sampled every 5 s can display as a 20 s oscillation that no instrument in the plant is producing.

Why this derivation matters commercially: it converts “the client wants one second” into “this measurement has a 30-minute time constant, so 60–180 s reproduces it to better than 10 % per step; the one-second budget is better spent on the discharge pressure, whose surge has a 4-second period and needs 0.4 s to be seen at all.” That is an engineering argument, and it wins.

DERIVATION 3 · AVAILABILITY WITH COMMON CAUSE STRETCH
SINGLE UNIT. Over a long period the unit is up for MTBF and down for MTTR in each cycle, so: A = MTBF/(MTBF + MTTR) U = 1 − A = MTTR/(MTBF + MTTR) n IN PARALLEL, ASSUMING INDEPENDENCE. All n must be down together: Uideal = Un For U = 4×10⁻⁴ and n = 2 this is 1.6×10⁻⁷ — five seconds a year, a figure no real installation has ever demonstrated. The model is wrong, not unlucky. THE β-FACTOR MODEL. Split each unit's failures into two populations: a fraction β that are COMMON CAUSE — they take the whole group down a fraction (1−β) that are INDEPENDENT Ugroup = β·U + (1 − β)·Un n = 2, U = 4.00e−4, β = 5 %: = 0.05(4.00e−4) + 0.95(1.60e−7) = 2.00e−5 + 1.52e−7 = 2.02e−5 \______/ \______/ 99.2 % of it 0.8 % of it TWO CONCLUSIONS, BOTH IMPORTANT: 1. THE FLOOR. As n → ∞, Ugroup → β·U. No amount of redundancy can take you below the common-cause term. Adding a third unit here changes the answer by 0.8 % — effectively nothing. 2. WHERE THE MONEY GOES. Halving β halves the group unavailability; halving U barely moves it. So spend on INDEPENDENCE — separate power, separate host, separate room, staggered patch windows, different firmware versions, procedures that two different people can follow — not on more identical boxes. The identical algebra governs protective layers (A52) and defence in depth (A54). It is one of the most transferable results in engineering.
DERIVATION 4 · THE WATCHDOG NUISANCE RATE STRETCH
Let each poll fail independently with probability L, and let the comms alarm require k CONSECUTIVE failures. P(a given poll starts a run of k failures) = Lk Polls per day at interval T: 86 400/T Expected nuisance alarms per day ≈ (86 400/T) · Lk (An upper bound: overlapping runs are counted more than once, so the true figure is slightly lower — which is the safe direction for a design.) Detection delay for a GENUINE failure = k · T THE TRADE, TABULATED (L = 2 %, T = 2 s, one site): k nuisance/day delay 1 864 2 s 2 17.3 4 s 3 0.35 6 s 4 0.007 8 s Each increment of k multiplies the nuisance rate by L — a factor of 50 here — and adds only T to the delay. The first two increments are the best value in the whole module. CHOOSING k PROPERLY, IN TWO STEPS: 1. Detection delay must be small compared with the process time constant: require k·T ≪ τ. With τ = 1800 s, k·T = 6 s is 0.3 % — free. 2. Then pick the smallest k that puts the SYSTEM-WIDE rate (multiply by the number of sites) inside your alarm budget (page 11). THE ASSUMPTION, STATED HONESTLY: real packet loss is BURSTY, not independent, so consecutive failures are more likely than Lk predicts and the nuisance rate will be somewhat worse than the formula. Two consequences: measure rather than trust the arithmetic, and treat a design that needs k ≥ 5 as evidence that the LINK needs fixing (P6).
SEVEN TRAPS THAT COST MARKS AND CONTROL ROOMS
#The trapThe correction
1Promising a scan rate before measuring the linkTcycle = N · n · (RTT + tdev). Measure RTT for a week, in bad weather, then promise
2Thinking bandwidth fixes latencySerialisation time is milliseconds; RTT is hundreds. Buy concurrency and scan classes, not megabits
3Substituting zero, or holding the last value, for a failed inputMark BAD, propagate, show it. Zero is a fact; unknown is a different fact (page 7)
4Timestamping on receipt and then reasoning about event orderTimestamp at source with a synchronised clock, or write the limitation into the report (P4)
5Believing the parallel-redundancy formulaU = βU + (1−β)Un. Common cause usually dominates by two orders of magnitude
6Lengthening the watchdog timeout to stop nuisance alarmsIncrease k, alarm once per site, and gate process alarms on quality. Lengthening the timeout hides blindness (page 11)
7Compressing history to save diskDisk is cheap; the incident that needs the missing detail is not. Set deviation from what you must SEE, and never compress evidence (WE2)

An eighth, unnumbered because it is organisational: letting a SCADA system be commissioned without a named owner, a backup that has been restored, and a quarterly review of six KPIs. Every decayed system in the country was configured correctly once. What it lacked was somebody whose job it was to notice the decay.
