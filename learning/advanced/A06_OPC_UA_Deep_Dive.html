Eleven Days of Perfect, Good-Quality, Completely Wrong Data

A PET BOTTLING PLANT, BIYAGAMA — THREE LINES, TWENTY-SIX SERVERS

Eighteen PLCs with embedded OPC UA servers, four robot controllers, two vision systems, two protocol gateways. One MES client, one historian client, one shift dashboard. About 4,300 nodes in the browse tree and a project everyone was proud of, because it replaced a mess of Modbus register maps with something that had names.

Three separate things went wrong. Only one of them ever produced an error message.

Fault 1 — the silent one. A controls engineer added a global data block to the Line 2 PLC on a Tuesday. Routine work, tested, signed off. Nothing broke. For the next eleven days the MES trended filler head torque on Line 2 with Good quality, fresh timestamps and a perfectly plausible shape — except the numbers were the conveyor speed. The client had stored its node identifiers as ns=4;s=Filler.Head3.Torque. The 4 is a namespace index: a position in an array the server publishes, not a name. Adding the data block changed that array, the model namespace moved from index 4 to index 5, and every cached identifier in the MES silently rebound to whatever now sat at index 4. Eleven days of OEE and quality reports were built on it, and a maintenance team spent two of those days investigating a filler head that was perfectly healthy.

Fault 2 — the visible one. The dashboard was specified at 100 ms and updated in lurches. The chain of causes is the most common one in the whole of OPC UA:

requested publishing interval = 100 ms server's minimum on that CPU = 200 ms → revisedPublishingInterval = 200 ms (the client never read the revised value back) network + client handler = 200 ms RTT + 100 ms processing = 300 ms outstanding PublishRequests, W = 1 T_eff = max( T_pub , (RTT + t_client) / W ) = max( 0.200 , 0.300 / 1 ) = 0.300 s — 3× slower than requested raise W from 1 to 2: T_eff = max(0.200 , 0.150) = 0.200 s (the server's floor) cost of that change: one integer in the client configuration.

Worse, the client's keep-alive watchdog had been set to three times the requested 100 ms — 300 ms — so it kept deciding the subscription was dead, tearing the session down and rebuilding it. Each rebuild re-browsed the tree one node per service call:

4,300 nodes × 200 ms round trip, one node per call = 860 s = 14.3 minutes batched at MaxNodesPerRead = 100: ceil(4300/100) = 43 calls × 0.2 s = 8.6 s a 100× improvement, and the server permitted it all along with ~40 reconnects per shift: 40 × 14.3 min = 9.6 hours of re-browsing inside an 8-hour shift — the client could never finish catching up before it fell over again.

Fault 3 — the one that is still there. All twenty-six application instance certificates were generated during the factory acceptance test in the same week, with two-year validity. Twenty-three months later the whole plant's OPC UA links failed inside a five-day window, the first at 02:10 on a Poya holiday. There was no certificate manager, no renewal procedure and no one on shift who had ever seen a trust list. The night team restored production the only way they could find in an hour: they set every endpoint to SecurityPolicy None, MessageSecurityMode None. That configuration is still running today, which means the plant's entire information model is readable — and writable — by anything that can reach TCP port 4840.

Nothing here is exotic. Every one of these three faults is a direct consequence of a design feature of OPC UA that the engineer did not know was a design feature: namespace indices are positional (page 4), publishing is a credit window, not a timer (page 8), services have negotiable operation limits (page 7), and security is mandatory-by-architecture but optional-by-configuration (page 9). All three are diagnosed here and fixed on page 14.

⚡ PREDICT FIRST

Fault 1 produced eleven days of wrong data with Good quality. Which measure would have caught it fastest?

B. The namespace index is a position in the server's NamespaceArray (NodeId i=2255), and servers are entirely within their rights to renumber it after a configuration change, a firmware update or a restart. The namespace URI is the stable identity; the index is a compression trick for the wire. A correct client reads NamespaceArray on every session activation, maps URI → current index, and rebuilds its NodeIds — or better, stores the browse path (/Objects/Line2/Filler/Head3/Torque) and calls TranslateBrowsePathToNodeId to obtain a fresh NodeId. Page 4 gives the full rule and the three-line reconnect procedure.

A protects the channel, not the meaning. Encryption guarantees that the wrong value arrives unaltered. Nothing about integrity or confidentiality addresses a client that is asking for the wrong node — a point worth remembering whenever “we have security” is offered as an answer to a data-trust question.

C makes it worse, faster. The data was already fresh; freshness was never in question. Increasing the rate multiplies a wrong number, and on this server it would simply have been revised back down anyway (page 8).

D duplicates the fault. Redundancy protects against a server failing, and this server never failed. Redundancy applied to a semantic error just gives you two identical wrong answers with a high availability figure attached.

Not a Protocol. A Way of Carrying Meaning.

THE DEFINITION CORE

OPC UA (IEC 62541) is a service-oriented, platform-independent framework for industrial interoperability that combines three things a fieldbus does not have together: a transport, a set of services, and an information model that describes what the data means, published by the server itself and discoverable at run time.

Read that as three promises, because they are what the standard is judged on:

  • 1
    Interoperability without a shared document. A client that has never seen your machine can connect, browse the tree, discover that a node is an AnalogItemType in bar with a range of 0–100, and display it correctly — with no register map, no CSV, no telephone call to the integrator.
  • 2
    Security as an architectural element, not an add-on. Authentication, signing, encryption, user identity and auditing are defined in the specification itself, at the session and channel layer — not bolted on by a VPN afterwards (page 9).
  • 3
    One model, many transports. The same information model can be served over opc.tcp binary to a plant client, over HTTPS to a corporate application, or published over MQTT as JSON to a cloud broker (pages 10 and 11). The semantics do not change with the pipe.
WHERE IT CAME FROM, AND WHY THAT MATTERS STRETCH

Classic OPC — OPC DA, HDA and A&E, from 1996 onwards — solved a real and urgent problem: every SCADA package needed a different driver for every PLC, so the number of drivers grew as products × devices. Classic OPC turned that into products + devices by standardising the interface. It worked, and it is still in service in thousands of plants.

But it was built on Microsoft COM/DCOM, and that inheritance defined its limits: Windows only; DCOM's dynamic port allocation and unfriendly timeouts made it a nightmare through a firewall; there was no security model worth the name; and — the deepest limit — it carried values, not meaning. A DA item was a string and a variant. Everything else lived outside the system.

OPC UA, first released in 2006 and adopted as IEC 62541, was a clean redesign rather than a port. The four things it changed are exactly the four things you will spend this module on:

OPC Classic (DA/HDA/A&E)OPC UA (IEC 62541)
PlatformWindows / COM / DCOMAnything — PLC firmware, Linux, RTOS, cloud, a browser
FirewallsDCOM dynamic ports — effectively impossibleOne TCP port (4840 by default), reverse connect available
SecurityWindows ACLs, no message securityX.509 application certs, signing, encryption, user tokens, audit
DataA flat list of item strings and variantsA typed, navigable object model with references
DiscoveryEffectively noneBrowse the live address space; LDS / GDS / mDNS discovery
ScopeData access, history, alarms — three separate specificationsOne unified model covering data, history, events, alarms, methods, programs
Communication patternClient–server onlyClient–server and publish–subscribe (page 11)

There is a lesson in that history that outlives the technology: the constraint that eventually kills an interface standard is rarely its data rate. It is its coupling to a platform and its inability to describe itself.

WHAT OPC UA IS NOT CORE

More projects are damaged by putting OPC UA in the wrong layer than by any technical fault in it. Be ruthless about this:

  • 1
    It is not a fieldbus and not a motion bus. Client–server OPC UA over TCP has millisecond-to-tens-of-milliseconds latency with no jitter guarantee. Servo loops, safety interlocks and drive synchronisation belong on EtherCAT, PROFINET IRT or CAN. OPC UA PubSub over TSN changes this materially for controller-to-controller traffic (pages 11 and A37) — but it does not turn plain opc.tcp into a deterministic bus.
  • 2
    It is not a safety protocol. There is no OPC-UA-based functional safety layer you may use for a stop function. Safety travels on PROFIsafe, FSoE, CIP Safety or hard wiring, and is assessed under IEC 61508 / ISO 13849 (A52, A35).
  • 3
    It is not automatically lightweight. A full server with security, subscriptions and history on a small CPU is a real load. Embedded profiles exist precisely because the full stack does not fit everywhere (page 3).
  • 4
    It is not interoperability by itself. Two conformant servers can model the same machine in two incompatible ways. The thing that actually delivers plug-and-play is the companion specification (page 12), and if your project has not chosen one, you have bought a protocol, not an integration.
  • 5
    It is not secure by default in practice. The specification defines strong security; the shipped configuration is frequently None, and page 1 shows how easily an operations decision at 02:00 makes it permanent.
⚡ PREDICT FIRST

A vendor says their new machine “supports OPC UA”. What single follow-up question tells you the most about how much integration work you are buying?

B. “Supports OPC UA” guarantees only that something will answer on port 4840 and let you browse. It says nothing about what you will find when you browse. Two conformant servers for two identical filling machines can expose Motor1.Spd and DriveA.ActualVelocity — both perfectly legal, both requiring a bespoke mapping and a document that will be lost. A machine that implements PackML / Euromap 77 / VDMA umati exposes an agreed structure, so the MES integration becomes configuration instead of development, and the second machine of that type costs almost nothing to add (page 12).

A, C and D are all good questions and you should ask all three — sampling rate and server placement decide your subscription design (pages 8 and 14), and security support decides whether page 9 is available to you at all. But they are questions about capacity and mechanism. B is the question about meaning, and meaning is the entire reason to choose OPC UA over a cheaper protocol in the first place.

CLIENT–SERVER AND PUBLISH–SUBSCRIBE: TWO ARCHITECTURES, ONE MODEL CORE

EVERYTHING IS A NODE CORE

The server's entire contents — values, machines, methods, data types, even the definitions of the reference types themselves — are nodes in one graph. A node has attributes (data it holds) and references (typed, directed links to other nodes). That is the whole model.

Two of these deserve a second look. Method is the one most projects forget exists: instead of writing a magic value into a command register and polling a status register, a server can expose ResetCounters(), StartRecipe(recipeId) or Calibrate() with typed arguments and a return status. That is a far better interface, and it is one Call service away. ReferenceType being a node is what makes the model self-describing: a client that meets an unfamiliar reference can browse to its definition and learn what it means.

REFERENCES: THE PART PEOPLE SKIP STRETCH

References are typed and directed, and they form a hierarchy of their own, rooted at References:

References ├─ HierarchicalReferences (build the browse tree) │ ├─ HasChild │ │ ├─ HasComponent “is a part of” (inverse: ComponentOf) │ │ ├─ HasProperty “describes” (inverse: PropertyOf) │ │ └─ HasSubtype “specialises” (inverse: SubtypeOf) │ ├─ Organizes “is filed under” (a folder relationship) │ └─ HasEventSource / HasNotifier (how events propagate upward) └─ NonHierarchicalReferences (meaning, not structure) ├─ HasTypeDefinition “is an instance of” ├─ HasModellingRule “is mandatory / optional” ├─ HasEncoding / HasDescription └─ vendor and companion-spec types (e.g. “Controls”, “IsPartOf”, “Feeds”)
  • 1
    HasComponent versus HasProperty is a real distinction. A component is part of the thing and can itself be complex; a property is metadata about the node and must be a simple leaf. EngineeringUnits and EURange are properties. A filler head is a component. Getting it backwards makes your model unreadable to generic clients.
  • 2
    Non-hierarchical references are where domain knowledge lives. “Pump P-101 feeds Tank T-201” is a relationship no folder tree can express, and it is exactly what an analytics or digital-twin application needs (A31). Most models never use them, which is why most models are just tag lists with indentation.
  • 3
    Browse is directional and filterable. Browse takes a reference type, a direction (Forward / Inverse / Both), a node-class mask and whether to include subtypes. Browsing everything from the root is the slowest possible way to find one node — filter, and use BrowseNext with continuation points when the result is capped (page 7).

⚡ PREDICT FIRST

Your client caches ns=4;s=Filler.Head3.Torque. The PLC is reprogrammed and a namespace is added. What is the most likely outcome?

B — and that ambiguity is the danger. The namespace index is a position in the server's NamespaceArray. If the array is reordered, index 4 now names a different URI. If no node with that identifier exists in the new namespace 4, you get BadNodeIdUnknown and you are lucky, because it is loud. But if the new namespace 4 happens to contain a node with a colliding identifier — which is common when a vendor namespace and a user namespace both use symbol-derived strings — you get a valid read of the wrong thing, with Good status, plausible values and no diagnostic anywhere. That is page 1, fault 1, eleven days long.

C is the belief that causes the fault. The identifier string may well be stable; the index in front of it is not. The stable identity is the namespace URI (for example http://plant.lk/Line2/), and the index is only a shorthand for it on the wire.

D is not a thing. There is no redirection mechanism, and a server has no way to know what your cached index used to mean.

The rule, in three lines: on every session activation, read Server/NamespaceArray (i=2255); map your stored URI to the current index; rebuild every NodeId. Where you can, store the browse path instead and call TranslateBrowsePathToNodeId. Treat a NodeId as a session-scoped handle, never as a permanent key in your database.

WHY TYPES ARE THE WHOLE POINT CORE

A tag list scales linearly with your effort: twenty filler heads is twenty mappings. A type-based model scales with the number of kinds of thing, not the number of things. One FillerHeadType and one client mapping written against it covers three heads today and thirty in 2031.

Concretely, a client that understands the type can do things a tag list can never support:

  • 1
    Find every instance without being told. Browse for nodes whose HasTypeDefinition points at FillerHeadType. A new head appears in the analytics on the day it is commissioned, with no configuration.
  • 2
    Generate displays and dashboards automatically. The type says what exists, the instance says what it reads, EURange says how to scale the axis, EngineeringUnits labels it. Whole HMI faceplates can be driven from the model (A14).
  • 3
    Compare like with like. “Show me the torque of every FillerHead in the plant” is a query, not a project. This is the foundation of the digital thread in A33 and the asset administration shell.

Use the standard variable types. AnalogItemType (with EURange, InstrumentRange, EngineeringUnits), TwoStateDiscreteType (with TrueState / FalseState texts) and MultiStateDiscreteType (with EnumStrings) are understood by every generic client on earth. Modelling a pressure as a bare Double and putting “bar” in the DisplayName throws that away for no saving at all.

EngineeringUnits uses UNECE Recommendation 20 codes — a numeric unitId plus display string, so “bar”, “degC” and “m3/h” are machine-comparable rather than strings a human has to interpret. That is the difference between a system that can detect a unit mismatch and one that quietly integrates litres into cubic metres.

DESIGNING A MODEL: A METHOD THAT SURVIVES REVIEW CORE
  • 1
    Start from the companion specification, always. Before drawing anything, check whether PackML, Euromap, VDMA/umati, the Devices (DI) spec or an ISA-95 model already covers your machine (page 12). Inventing a model that a standard already defines is the most common and most expensive mistake in this discipline.
  • 2
    Model the plant, not the PLC. The structure should mirror physical and functional reality — Site / Line / Machine / Unit / Signal — not the memory layout of a data block. The PLC will be replaced; the filling machine will not.
  • 3

The Variant is a self-describing container: a type identifier plus a payload, optionally with array dimensions. That flexibility is powerful and occasionally dangerous.

THE PUBLISH CREDIT WINDOW — THE THING NOBODY IS TAUGHT CORE

A server may not push data to a client whenever it likes. It can only respond to a request it is already holding. The client therefore sends PublishRequests in advance, and the server keeps them in a queue, consuming one for every notification message it sends. If the queue is empty, the notification waits, no matter what the publishing interval says.

Let W = number of PublishRequests the client keeps outstanding T_pub = revised publishing interval RTT = network round trip t_c = client time to process a notification and re-issue Effective notification interval: T_eff = max( T_pub , (RTT + t_c) / W ) Page 1: T_pub = 200 ms, RTT = 200 ms, t_c = 100 ms W = 1 → T_eff = max(200, 300) = 300 ms (3× the request) W = 2 → T_eff = max(200, 150) = 200 ms (the server's floor) W = 5 → T_eff = 200 ms (no further gain — the floor rules) Rule of thumb: W ≥ ceil( (RTT + t_c) / T_pub ) + 1, and never less than 2. Most SDKs default to 1 or 2; on a WAN link that default is the single most common cause of “OPC UA is slow”.

The second half of the story is that no data is lost when the window is short — the values queue in the MonitoredItem and arrive together. That is why the symptom is bursty data with correct timestamps rather than missing data, and why it is so often misdiagnosed as a network fault. If the queue also overflows, then values are lost, and the only evidence is the Overflow bit in the StatusCode of the first value that survives.

⚡ PREDICT FIRST

A subscription runs at 1 s publishing with 100 ms sampling and queueSize = 1. The value changes every 200 ms. What arrives?

B. With queueSize = 1 the MonitoredItem holds exactly one value. Each new sample overwrites the previous one (with discardOldest = true), so the publish carries the most recent value and nine tenths of the signal is gone permanently. The server sets the Overflow bit in the StatusCode of the delivered value, which is the only notice you will ever get — and almost no client displays it.

This is the correct configuration for a display: an operator watching a trend wants the current value once a second, not ten values. It is a serious defect for a historian or any analytics that depends on the shape of the signal. The fix is arithmetic, not judgement: queueSize ≥ ceil(publishing interval / sampling interval), here 1000/100 = 10, and the data arrives complete, correctly timestamped, in one message per second.

A is what people assume, and it is exactly what you get once the queue is sized properly — which is why the failure is invisible until somebody compares the historian against a scope trace.

C and D do not happen. The combination is perfectly legal and the server will not second-guess you. OPC UA revises what it cannot deliver (intervals) and silently obeys what it can (queue sizes).

⚡ PREDICT FIRST

A plant's OPC UA endpoints run SignAndEncrypt with Aes256, and user identity is Anonymous. An attacker gains a foothold on an engineering laptop that is already trusted. What can they do?

B. Encryption protects data in transit from a third party. It says nothing about what a legitimately connected application may do.   • 7

⚡ PREDICT FIRST

A cloud project pushes 4,300 items at 200 ms as JSON over MQTT on a 10 Mbps estate link. Roughly what happens?

B. 4,300 items every 0.2 s is 21,500 values per second. At about 30 bytes in UA Binary that is 645 kB/s ≈ 5.2 Mbps — already half the link. JSON multiplies it by roughly five, giving ~26 Mbps of payload on a 10 Mbps pipe. It does not degrade gracefully; the broker backs up, the publisher queues, latency grows without bound and eventually something drops.

Three fixes, in order of value: (1) a deadband — typically only 5–20 % of analogue items genuinely change beyond noise in any interval, which alone can take 26 Mbps to 3 Mbps; (2) honest rates — very few of 4,300 tags need 200 ms, and rate classes are as effective here as in A14; (3) UADP binary instead of JSON where the consumer can decode it.

C is a hope, not a design. MQTT does not compress payloads; TLS may, and you must not rely on it.

D confuses the protocol with the payload. MQTT's own header is famously tiny — two bytes — which says nothing about the twenty-six megabits you asked it to carry.

PubSub: One Publisher, Many Listeners, No Handshake

client–serverbrokered PubSubbroker-less PubSubbroker
WHY IT EXISTS CORE

Client–server does not scale in two directions. Upward, every extra consumer is another session, another set of monitored items and another slice of a controller's CPU. Sideways, controller-to-controller data over a stateful, acknowledged, session-based protocol is exactly the wrong shape for a 1 ms cyclic exchange. PubSub answers both: the publisher formats a dataset once and sends it once, and the number of consumers becomes a property of the network rather than of the device.

  • 1
    Broker-less (UDP multicast or raw Ethernet) is for the plant floor: lowest latency, no infrastructure, and with TSN scheduling it becomes genuinely deterministic. This is what makes OPC UA credible as a control-level network.
  • 2
    Brokered (MQTT or AMQP) is for everything upward: it traverses NAT and firewalls with outbound connections only, it survives thin and intermittent links, and it lets a cloud service subscribe without any route into the plant.
  • 3
    Both carry the same DataSet. One PublishedDataSet can feed a UADP writer group for the cell and a JSON-over-MQTT writer group for the cloud, from the same server, with the same semantics.
THE MESSAGE, AND WHY IT IS SMALLER STRETCH
A UADP NetworkMessage: NetworkMessage header publisherId, group, version, timestamp for the whole message └─ DataSetMessage writerId, sequence number, status └─ field, field, field, ... raw values, in a fixed agreed order Client–server: 30 B per value, every value self-contained UADP RawData : 4 B for a Float — no NodeId, no per-value status, no per-value timestamps, no client handle 100 Float fields: client–server ≈ 3,000 B UADP raw ≈ 400 B + ~40 B header roughly 7× smaller for cyclic data The price is exact: you have given up per-value status and timestamps, and you can no longer discover what field 37 means from the message itself. DataSetMetaData carries that — and it must reach the subscriber somehow.

Three field encodings exist and the choice is a real design decision: RawData (values only, smallest, requires agreed layout), DataValue (full status and timestamps per field — use where quality matters), and Variant (self-describing types, middle ground). Choosing RawData for a cyclic control exchange and DataValue for a quality-critical measurement in the same system is normal and correct.

PUBSUB SECURITY AND ITS AWKWARDNESS STRETCH

There is no handshake, so there is nowhere to negotiate keys. OPC UA solves this with a Security Key Service (SKS): publishers and subscribers authenticate to the SKS with normal client–server security, collect group keys for a security group, and use them to sign or encrypt NetworkMessages. Keys rotate on a schedule; a subscriber that misses a rotation goes deaf until it re-collects.

The consequences are practical. You now have an infrastructure dependency that must be as available as the data itself; anyone holding a group key can publish into that group, so key distribution is authorisation; and replay protection depends on sequence numbers and timestamps, which is another reason clock synchronisation is not optional. Where PubSub runs over MQTT, TLS to the broker plus broker ACLs is a legitimate simpler alternative — but note that it protects the hop, not the message, and the broker becomes fully trusted.

⚡ PREDICT FIRST

A dashboard, a historian, an MES and a cloud analytic all need the same 500 values at 1 s from a mid-range PLC that is already at 60 % CPU. What is the right architecture?

B. Four sessions means the PLC samples, filters, queues, signs and encrypts 2,000 monitored items instead of 500, and does it four times over — on a CPU with 40 % headroom that also has a machine to run. One subscription into a gateway, an aggregating OPC UA server or an edge node, which then serves the other three (by OPC UA, by PubSub over MQTT, or both), cuts the controller's load by four and adds buffering, protocol translation and a security boundary for free. A is what happens by default, because each consumer is delivered by a different supplier who only sees their own connection. It is the most common cause of a PLC that mysteriously slows down two years after commissioning.

C solves a communication problem with capital equipment and leaves you with two controllers to keep in step.

D degrades everyone's data to protect a controller from a load it should never have been given — and note it does not reduce the sampling work, only the publishing, so most of the cost remains.

THE ARGUMENT IN ONE PARAGRAPH CORE

⚡ PREDICT FIRST

A machine builder implements a companion specification but renames two mandatory members to match their internal terminology, keeping everything else. What breaks?

B. A companion specification is a contract expressed in BrowseNames. A conforming client resolves …/MachineIdentification/SerialNumber by name; if the server calls it MachineSerial, the lookup returns nothing and the client concludes the mandatory member is absent. Nothing errors, nothing logs, and the defect is discovered by the integrator months later — usually as “the standard does not work”.

This is why BrowseName is machine-readable and DisplayName is human-readable. Renaming for internal terminology is exactly what DisplayName and Description are for; it is free, it is localisable, and it breaks nothing.

A confuses shape with identity. There is no positional addressing in the address space — names are the addressing.

C does not happen: the server is perfectly valid OPC UA. It is simply not the model it says it is.

D is the mistake in reverse — and worth stating as a rule: DisplayName may change freely; BrowseName is an API and changing it is a breaking change.

EVENTS: NOT VALUES, AND NOT POLLED CORE

An Event is not stored in a node. It is generated by an object that is an event notifier, propagates up the HasNotifier / HasEventSource hierarchy, and is delivered to any client with an event MonitoredItem on a node in that path — usually the Server object, which sees everything.

Base event fields (BaseEventType), always present: EventId unique per occurrence — use it to correlate, never the time EventType the NodeId of the event's type — filter on this SourceNode what it happened to SourceName human-readable source Time when it happened (source time) ReceiveTime when the server got it Severity 1–1000 (map onto your priorities: see below) Message localised text Subscribing to events: CreateMonitoredItem( nodeId = Server (i=2253), attribute = EventNotifier, filter = EventFilter { SelectClauses: which fields I want back WhereClause: which events I care about } ) SelectClauses are mandatory. Ask for nothing and you receive events with no content — a very common first-attempt result.

The WhereClause is a small filter language with operators (Equals, GreaterThan, Like, And, Or, InList, OfType…) evaluated at the server. Filtering there instead of at the client is the difference between receiving every event in the plant and receiving the twelve that concern you.

ALARMS AND CONDITIONS, AND HOW THEY MEET ISA-18.2 STRETCH

A Condition is a stateful event: it persists, it can be refreshed, and it has the three independent sub-states drawn above. The type hierarchy runs BaseEventType → ConditionType → AcknowledgeableConditionType → AlarmConditionType, then specialises into LimitAlarmType (with HighHigh / High / Low / LowLow limits), DiscreteAlarmType, DeviationAlarmType, OffNormalAlarmType and others.

  • 1
    Acknowledge and Confirm are Methods on the condition, not writes to a bit. That gives you the caller's identity, a comment field and an audit event, for free — and it is the correct answer to “who silenced that alarm?”
  • 2
    ConditionRefresh is how a client gets the current alarm list. On connect (or after a gap) the client calls it and the server re-sends every active or unacknowledged condition. Without it, a newly started HMI shows an empty alarm banner on a plant full of alarms — a genuinely dangerous state.
  • 3
    Shelving is standardised: OneShotShelve, TimedShelve, Unshelve, with the remaining time visible. This is the ISA-18.2 shelving concept implemented in the protocol, so it is auditable rather than a private HMI feature.
  • 4
    Severity 1–1000 must be mapped, not copied. ISA-18.2 wants three or four priorities with different operator responses. Agree the bands in the alarm philosophy (A53) — for example 1–332 low, 333–665 medium, 666–1000 high — and apply them consistently across every server, or your rationalisation is meaningless.
  • 5
    Server-side alarming beats client-side alarming. If the server evaluates the condition, then every client agrees, the alarm exists during a network outage, and the event carries the source timestamp of the real transition rather than the moment a client noticed. Deriving alarms in the SCADA from polled values reintroduces every problem A14 spends a page on.
⚡ PREDICT FIRST

A client subscribes to a boolean HighTempAlarm variable at 1 s instead of subscribing to events. What does it lose?

B. A boolean carries one bit of the situation. Gone with it: transitions shorter than the interval (a 300 ms excursion at 1 s sampling is invisible — and short repeated excursions are precisely the signature of an incipient fault); the acknowledgement and confirmation states, so the HMI cannot distinguish “new” from “seen and still wrong”; severity, so everything looks equally urgent; the message, so the operator gets a tag name instead of a sentence; the EventId, so occurrences cannot be correlated; and the audit trail, so nobody can say who acknowledged what.

D is the tempting engineering answer and it is wrong in principle: no polling rate makes a sampled bit equivalent to an event, because the event is generated by the transition and carries its true source timestamp. Faster polling narrows the window and multiplies the load; it never closes the gap.

A and C both describe a system that will pass a factory acceptance test and then fail its first serious incident investigation — which is the moment the alarm history was supposed to earn its keep.

EIGHT IDEAS THAT CARRY THE WHOLE MODULE CORE
  • 1
    OPC UA carries meaning, not just values. The information model is the reason to choose it; if your project ends with a flat tag list, you have paid for a framework and used a protocol.
  • 2
    A NodeId is a session-scoped handle, not a database key. The namespace URI is the stable identity; re-resolve on every connect.
  • 3
    Types scale, tags do not. Model the kind of thing once, instantiate it many times, and the twentieth machine costs nothing to integrate.
  • 4
    Every value carries a status and two timestamps. Good means the delivery is sound — not that the number is true, current, or the one you meant.
  • 5
    Latency × operation count is the budget. Batch to MaxNodesPerRead; a hundredfold speed-up is usually sitting there unclaimed.
  • 6
    Publishing is a credit window. T_eff = max(T_pub, (RTT + t_c)/W). One integer — the outstanding PublishRequest count — explains most complaints about speed.
  • 7
    Security is architectural but optional in configuration, and the thing that actually fails is the certificate lifecycle, on a holiday, at 02:00.
  • 8
    Companion specifications are where the money is. They turn integration from O(N) into O(1), and they are free at purchase and unbuyable afterwards.
SIX WAYS OPC UA PROJECTS FAIL CORE
1 · The cached namespace index

A configuration change renumbers the NamespaceArray and a client silently reads the wrong node with Good quality. Detect: compare a known value against the HMI after any PLC change. Prevent: re-read NamespaceArray on every activation and bind by browse path.

2 · The credit window of one

W = 1 with a WAN round trip caps the notification rate regardless of the publishing interval. Detect: data arrives in bursts with correct timestamps. Prevent: W ≥ 3, and always read the revised interval back.

3 · The undersized queue

queueSize = 1 against a sampling ratio of 10 discards nine values in ten, permanently, with only the Overflow bit as evidence. Prevent: queueSize ≥ ceil(T_pub / T_sample) for anything that will be historised.

4 · The unbatched client

One node per Read turns a reconnect into fourteen minutes and a plant into a system that is permanently catching up. Detect: high call rate, low CPU, low bandwidth. Prevent: read OperationLimits and batch.

5 · The certificate cliff

A fleet issued in one week expires in one week, years later, out of hours. Prevent: a certificate register, staggered validity, planned renewal jobs, and a GDS above about twenty applications.

6 · “Temporarily” setting security to None

An emergency fix at 02:00 becomes the permanent configuration, exposing a fully self-describing model to anything that can reach the port. Prevent: a tested renewal procedure, and an annual audit that checks the endpoint list rather than the documentation.

QUICK CHECK — SIX QUESTIONS
Q1. Why is a NodeId unsafe to store permanently, and what should you store instead?
Tap to reveal ↓A: Because the namespace index is a position in the server's NamespaceArray and may be renumbered by a configuration change, firmware update or restart — and the resulting misbinding can be silent, delivering Good-quality data from a different node. Store the namespace URI plus the browse path, and on every session activation read Server/NamespaceArray (i=2255) to map URI to the current index, or call TranslateBrowsePathToNodeId to obtain a fresh NodeId. Treat NodeIds as session-scoped handles.
Q2. A subscription requests 100 ms publishing. The server revises it to 250 ms, the round trip is 180 ms, the client takes 60 ms per notification, and W = 1. What is the effective interval, and what single change helps most?
Tap to reveal ↓A: T_eff = max(T_pub, (RTT + t_c)/W) = max(250, 240/1) = 250 ms — here the server's floor already dominates, so W = 1 is just adequate. Raising W to 2 gives max(250, 120) = 250 ms, no change. The single most useful change is to accept 250 ms and configure everything else from it: set the client watchdog from the revised keep-alive, and set queueSize ≥ ceil(250/samplingInterval) so nothing is discarded. Note how the answer flips if the link degrades: at RTT 400 ms, W = 1 gives 460 ms and W = 2 restores 250 ms — which is why W ≥ 3 is the safe default rather than an optimisation.
Q3. Distinguish sampling interval, publishing interval and queue size in one sentence each.
Tap to reveal ↓A: Sampling interval (per MonitoredItem) is how often the server looks at the source — it decides what is seen. Publishing interval (per Subscription) is how often accumulated notifications are packaged and sent — it decides what is delivered. Queue size (per MonitoredItem) is how many samples are held between publishes — it decides how much of what was seen survives to be delivered. The relationship that matters: queueSize ≥ ceil(publishing / sampling), or the excess is discarded with the Overflow bit set.
Q4. Why does encrypting the channel not protect you from a compromised but trusted client?
Tap to reveal ↓A: Encryption is confidentiality and integrity in transit — it protects against an eavesdropper or a tamperer between the endpoints. A trusted client is one of the endpoints; everything it sends is legitimately signed and decrypted by the server. Protection at that layer comes from the second identity: named user authentication instead of Anonymous, role-based access control, UserAccessLevel restricting writes per node, network segmentation so the client cannot reach servers it has no business with, audit events, and certificate revocation so a lost machine can be excluded quickly.
Q5. A client reads 6,000 nodes on connect, one per call, over a 120 ms link. How long, and what should it do instead?
Tap to reveal ↓A: 6,000 × 0.120 s = 720 s = 12 minutes of pure round-trip latency, with the network and both CPUs nearly idle throughout. Instead: read Server/ServerCapabilities/OperationLimits/MaxNodesPerRead; if it is 500, then ceil(6000/500) = 12 calls × 0.120 s = 1.44 s, a 500× improvement with no other change. Better still, do not re-read on reconnect at all — use TransferSubscriptions and Republish so the subscription survives and the missed notifications are recovered.
Q6. What does a companion specification add that plain OPC UA conformance does not, and how do you get it?
Tap to reveal ↓A: It adds an agreed information model for a class of machine — the same types, BrowseNames, units and states on every conforming device — so a client mapping written once works for every machine of that type, present and future. Plain conformance only guarantees that browsing works, not that what you find is recognisable. You get it by writing it into the purchase specification with a version (“shall implement OPC 40001-1 and PackML”), verifying it at FAT by browsing with an independent client against the specification document, and extending it only by subtyping in your own namespace — never by renaming standard BrowseNames.

WE3 — SIX TEA FACTORIES TO A CLOUD ANALYTIC OVER 4G

Brief. Six factories, 700 items each, wanted at 1 s, published to a Colombo analytics platform. Each site has a 4G router with about 2 Mbps of usable uplink and a metered data plan. Analogue tags have a span of 100 units and about 0.3 units of noise; a 0.5 % deadband is proposed. Decide the encoding and the filtering, and cost the data.

Raw rate: 6 × 700 = 4,200 items at 1 s = 4,200 values/s (all sites) UA Binary, no deadband: 4200 × 30 B = 126 kB/s = 1.01 Mbps UA JSON, no deadband: 4200 × 150 B = 630 kB/s = 5.04 Mbps ✗ Deadband effect (derivation 4): D = 0.5 % × 100 = 0.5 units, σ = 0.3 D/σ = 1.667 → reporting fraction = 2Q(1.667) = 9.6 % With deadband: 4200 × 0.096 = 401 values/s UA Binary: 12.0 kB/s = 96 kbps → 1.04 GB/day → 31 GB/month UA JSON : 60.2 kB/s = 482 kbps → 5.20 GB/day → 156 GB/month

Decision and reasoning. JSON without a deadband is impossible — 5 Mbps into 2 Mbps does not degrade, it collapses. JSON with a deadband fits the link technically but costs five times the data volume for the convenience of a text format nobody reads. Use UADP or UA Binary over MQTT with the deadband, and reserve JSON for a small, low-rate diagnostic topic that a human genuinely inspects.

Two engineering caveats that belong in the report. First, the 9.6 % figure assumes independent noise about a steady value; a signal that is genuinely ramping reports at roughly |dx/dt|/D regardless of noise, so a plant that is actually moving will report more (derivation 4). Second, a deadband is lossy and permanent — agree with the data consumer, in writing, that 0.5 % resolution is acceptable for their analysis before the first byte is filtered, because no one can recover it afterwards.

WE4 — THE CERTIFICATE CLIFF, COSTED

Brief. The page-1 plant: 26 servers, 3 clients, self-signed certificates, 2-year validity, all issued within one week at FAT. Twelve engineer-minutes per manual trust operation. Quantify the exposure and propose a scheme.

Self-signed, pairwise trust: trust operations = S × C × 2 (both directions) = 26 × 3 × 2 = 156 engineer time = 156 × 12 min = 1,872 min = 31.2 hours and all 156 fall due inside the same five-day window, at month 24, starting at 02:10 on a holiday. CA-issued hierarchy: each application trusts ONE issuer certificate trust operations = S + C = 29 → 29 × 12 min = 5.8 hours renewal is per-certificate and can be scheduled GDS + CertificateManager (push or pull): issuance, renewal and revocation automated; human effort ≈ exception handling only Staggering, whatever the scheme: 29 certificates over 24 months = ~1.2 renewals per month — a maintenance task, not an outage.

Recommendation. Move to a CA hierarchy now (it removes 80 % of the manual work with no new infrastructure), deploy a GDS if the site grows past about twenty applications, stagger the validity periods immediately by re-issuing in tranches, and record every expiry in the CMMS as a planned job with 60 days of lead time. Add one line to the standard: no certificate shall be issued with the same expiry month as more than five others.

And the honest note for management: the outage did not happen because the certificates expired. Certificates expiring is the design working correctly. It happened because nobody owned the expiry date — which is an asset-management failure, not a technology failure, and it is fixed with a register and a name.

WE5 — FOUR CONSUMERS, ONE TIRED PLC

Brief. A dashboard, a historian, an MES and a cloud analytic each want the same 500 values at 1 s from a PLC already at 60 % CPU. Compare direct connection with an aggregating edge gateway.

DIRECT: 4 sessions × 500 monitored items = 2,000 items on the PLC sampling = 2,000 samples/s notifications = 2,000/s, each signed and encrypted payload out = 2000 × 30 B = 60 kB/s (×4 encryption work) plus 4 sessions, 4 subscriptions, 4 keep-alives, 4 reconnect storms GATEWAY: 1 session × 500 items = 500 items on the PLC sampling = 500 samples/s (4× less) notifications = 500/s (4× less) the gateway fans out to 4 consumers on hardware that costs less than an hour of the line's downtime Additional benefits of the gateway, at no extra cost: • store-and-forward across a WAN outage • protocol translation (MQTT/JSON) • a security boundary and one place to patch • one namespace for the cell • the PLC's client list stops growing every time a new project starts

The counter-argument, stated fairly: the gateway is a new single point of failure and another device to own, patch and certificate-manage. That is real. It is answered by treating the gateway as plant equipment — on the UPS, in the maintenance system, with a spare on the shelf and a configuration backup — and by noting that its failure costs visibility, while an overloaded PLC costs production. Where the two risks are not equivalent, put the fragility where it hurts least.

(ii) Clock discipline over 4G is weak, so cross-site sequence claims must be avoided. (iii) Certificate management across six unmanned sites is the hardest ongoing task — specify a GDS or a CA and a renewal procedure from day one.
P10 · (12 marks) Synthesis. After a quality escape, a plant manager instructs: “Put every tag in the plant on a 100 ms subscription to the cloud so we never miss anything again, and turn security off on the OPC servers so the data scientists can connect without waiting for IT.” There are 18,000 tags across 22 servers on a 20 Mbps site link. Respond as the engineer.
Tap to reveal ↓1 — Price the instruction as given (3). 18,000 tags at 100 ms = 180,000 values/s. At 30 B binary that is 5.4 MB/s = 43 Mbps, more than twice the site link; as JSON it is over 200 Mbps. The sampling load alone — 180,000 samples/s spread over 22 controllers, roughly 8,200/s each — would put most of those PLCs into overload before a single byte left the plant. The instruction is not expensive; it is impossible, and saying so with the arithmetic is the first professional act.

2 — Address the real requirement (3). The requirement is not “100 ms everywhere”; it is “we must be able to reconstruct what happened during a quality escape”. That is served by: the right 100–200 tags at 100–200 ms (the ones that move on the timescale of the defect), correct source timestamps and synchronised clocks, event and alarm history rather than sampled bits, and adequate queue sizes so nothing is discarded. A rate class design over 18,000 tags typically lands near 2,000–4,000 values/s — about 1 Mbps — and reconstructs the incident better than the 43 Mbps version, because the fast tags are actually fast and the slow ones are not drowning them.

3 — Refuse the security instruction, and say why in their terms (3). Disabling security exposes a self-describing model — one that tells any visitor exactly what every node means — to anything that can reach the port, with write access wherever AccessLevel permits. The realistic consequence is not an abstract breach but an unplanned line stop from an accidental write, and an insurance and customer-audit exposure that costs more than the escape did. This is a decision the manager is not authorised to take alone; it belongs to whoever owns plant risk.

4 — Give them something better, this week (3). A read-only data-science endpoint on the edge gateway, with its own named identity, Observer role, no write permissions, its own certificate and rate limits — available in days, no change to any controller, no exposure of the control layer. Plus a written commitment on the tag list and rates, and a 30-minute acceptance test that proves the incident-reconstruction capability. The escape is answered, IT's queue is bypassed legitimately, and nothing is left switched off afterwards.

Derivations

Four results, proved. An examiner will accept a formula you can derive and will probe one you have merely quoted.

D1 — THE EFFECTIVE NOTIFICATION INTERVAL AND WORST-CASE DATA AGE

Setup. The server may only transmit a NotificationMessage in response to a PublishRequest it already holds. Let the client keep W requests outstanding. Each request is consumed by one notification; the client re-issues it after receiving and processing the response.

A single request's round trip: issue → (network out) → server holds it → notification → (network back) → client processes → re-issue Time for one credit to become available again: T_cycle = RTT + t_c With W credits circulating independently, the client can absorb one notification every T_cycle / W on average — this is exactly the window/round-trip throughput argument used for TCP windows: rate_max = W / (RTT + t_c) The server also cannot send faster than its own publishing clock: rate_pub = 1 / T_pub (T_pub = the REVISED interval) The achieved rate is the smaller of the two, so the achieved interval is the larger of the two: T_eff = max( T_pub , (RTT + t_c) / W ) (1) Two regimes: (RTT + t_c)/W ≤ T_pub → publishing-limited — more W buys nothing (RTT + t_c)/W > T_pub → credit-limited — more W is free speed Setting (RTT + t_c)/W ≤ T_pub and solving for W gives the design rule W ≥ ceil( (RTT + t_c) / T_pub ) + 1 (2) The +1 is margin for jitter: RTT is a distribution, not a number, and a single late round trip must not stall the pipeline.

Worst-case age. A change occurring just after a sample is missed until the next sample (up to Tsample), then waits for the next delivery (up to Teff), then travels (RTT/2), plus any time spent behind other values in the queue:

A_max = T_sample + T_eff + RTT/2 + t_queue (3) Page-1 numbers: 200 + 300 + 100 = 600 ms for a system sold as 100 ms. Two consequences worth stating in a design review: • Age is dominated by whichever of sampling and delivery is slower; halving a sampling interval while T_eff is 300 ms buys almost nothing. • NOTHING in the DataValue announces this age. The only way to know it is to compare SourceTimestamp with a synchronised local clock — which is why clock discipline is a data-quality control, not an IT nicety.

Important honest note. Equation (1) is a first-order model. It assumes the server has data ready at every publishing tick, that credits are consumed one per message, and that RTT is stable. It ignores maxNotificationsPerPublish (which can split one interval's data across several messages, consuming several credits) and server-side queueing under load. It is nonetheless the right model for design: it predicts the observed behaviour of real systems to within the accuracy of the RTT estimate, and it identifies the correct control variable.

D2 — THE BYTE BUDGET OF A NOTIFIED VALUE

Setup. UA Binary is a position-based, little-endian encoding: no field names travel, and structures are written in a fixed order. Build a MonitoredItemNotification containing a Float from the bottom up.

DataValue: EncodingMask (which optional fields follow) 1 B Value: Variant encoding byte (built-in type id + array flags) 1 B Float payload 4 B StatusCode (UInt32) 4 B SourceTimestamp (Int64, 100 ns ticks from 1601) 8 B ServerTimestamp (Int64) 8 B ───── DataValue subtotal 26 B MonitoredItemNotification: clientHandle (UInt32) 4 B ───── per reported value 30 B (4) By type: Boolean 1 B payload → 27 B Double 8 B → 34 B Int32 4 B → 30 B String 4 + n → 30 + n B Per message, once: chunk header + sequence header ≈ 32 B NotificationMessage (sequence no, publish time, array headers, DataChangeNotification) ≈ 40 B signature, MessageSecurityMode = Sign 32 B + padding, SignAndEncrypt (AES block 16 B) ≈ +16 B Aggregate bandwidth: B = Σ_i ( n_i × f_i / T_eff,i ) × b + overhead / T_eff (5) n = items, f = fraction reporting (deadband), b = bytes per value

Three readings of equation (4) that change designs. First, 16 of the 30 bytes are timestamps — 53 % of the payload. A server that can be configured to omit ServerTimestamp on a subscription saves 27 % instantly, and PubSub's RawData encoding — which drops both timestamps, the status and the handle — reaches 4 B for the same Float, roughly 7× smaller. That is the whole efficiency argument for UADP in one line. Second, the per-message overhead of ~100 B is negligible when a message carries hundreds of values and dominant when it carries one — another argument against per-item subscriptions. Third, JSON's 4–6× multiplier comes from field names, quoted numerals and ISO-8601 timestamp strings; it is a real cost paid for human readability, and it should be a deliberate choice rather than an SDK default.

D3 — THE BATCHING LAW AND WHEN LATENCY DOMINATES

Setup. A client must operate on n nodes. The server permits M nodes per service call. Each call costs a round trip RTT plus server work; let the server spend tnode per node and tfix per call.

N_calls = ceil( n / M ) (6) T_total = N_calls × ( RTT + t_fix ) + n × t_node (7) The first term is latency you pay per call; the second is work you pay per node and cannot be batched away. Substituting N ≈ n/M: T_total ≈ n × [ (RTT + t_fix)/M + t_node ] (8) Latency dominates whenever (RTT + t_fix) / M > t_node i.e. M < (RTT + t_fix)/t_node (9) Example: RTT = 200 ms, t_node = 0.2 ms → latency dominates for any M below 1,000. On a WAN, essentially every real batch size is in the latency-dominated regime, which is why batching feels like magic. Asymptotes: M = 1 → T = n(RTT + t_fix + t_node) — the pathological case M → ∞ → T → n × t_node — the irreducible floor Page-1 check, n = 4,300, RTT = 200 ms, t_node = 0.2 ms: M = 1 : 4300 × 0.2002 = 861 s M = 100 : 43 × 0.2 + 4300 × 0.0002 = 8.6 + 0.86 = 9.5 s M = 1000 : 5 × 0.2 + 0.86 = 1.9 s floor : 0.86 s — you cannot do better, and you do not need to.

The generalisation worth carrying out of this module: equation (9) is the same statement as the poll-budget argument in A14 and the round-trip argument in A01. Whenever a protocol conversation is request–response over a link with meaningful latency, the number of exchanges — not the number of bytes — is the budget. Bandwidth graphs will not show it, CPU graphs will not show it, and it will be blamed on the network every time.

D4 — WHAT A DEADBAND ACTUALLY REMOVES

Setup. A MonitoredItem reports only when the new sample differs from the last reported value by more than D. Model the measurement as a constant true value plus independent Gaussian noise of standard deviation σ.

Let x_k = μ + ε_k , ε ~ N(0, σ²), independent. Take the last reported value as ≈ μ. A sample is reported when |x_k − μ| > D P(report) = P(|ε| > D) = 2 × Q(D/σ) (10) where Q(z) = 1 − Φ(z) is the standard normal tail. Reporting rate: r = f_s × 2Q(D/σ) , reduction factor 1/(2Q(D/σ)) D = 1σ → 31.7 % report (reduction 3.2×) D = 2σ → 4.55 % report (reduction 22×) D = 3σ → 0.27 % report (reduction 370×) WE3's case: span 100, D = 0.5 % = 0.5, σ = 0.3 → D/σ = 1.667 2Q(1.667) = 9.6 % → a 10.5× reduction. Note the extreme sensitivity: the reduction is exponential in (D/σ)², so a deadband quoted as “0.5 %” means nothing until you know σ.

The honest limits of equation (10) — and this is where marks are won:

  • 1
    Real noise is correlated. Successive samples of a filtered instrument are not independent, so the true reporting rate is usually lower than (10) predicts. Equation (10) is therefore a conservative estimate for sizing a link — which is the direction you want to be wrong in.
  • 2
    A moving process defeats the noise model entirely. If the true value ramps at rate v = |dx/dt|, the deadband is crossed every D/v seconds no matter how small σ is: r ≈ v/D. A tank filling at 2 units/s with D = 0.5 reports 4 times a second, forever. So a deadband quantises a moving signal and filters a still one — and a plant that is genuinely running is full of moving signals. Size links for the moving case.
  • 3
    Percent deadband needs an EURange. Without it the server has nothing to take a percentage of, and behaviour varies between implementations. This is the practical reason to model analogue values as AnalogItemType (page 5).
  • 4
    The loss is permanent and asymmetric. Deadband is applied before transmission, so no consumer can recover the filtered samples. A brief spike smaller than D is invisible to every system downstream, forever — which is precisely why evidential, regulatory and fault-diagnosis tags should have no deadband at all, however tempting the bandwidth saving.
SEVEN TRAPS THAT COST MARKS AND PLANTS
TrapThe correct statement
“The NodeId is the tag's permanent address”It is a session-scoped handle. The namespace URI plus browse path is the identity; re-resolve on every connect.
“I asked for 100 ms so I get 100 ms”The server revises intervals, queue sizes, lifetime and keep-alive. Read the revised values and configure everything else from them.
“Good quality means the value is correct”Good means the delivery is sound. It says nothing about calibration, staleness, or whether the node is the one you meant.
“Bigger publishing interval = less server load”It reduces notification load only. Sampling load is set by the sampling interval and does not change.
“Encryption secures the system”Encryption secures the channel. Authorisation is the user identity, roles and UserAccessLevel — a different question entirely.
“It supports OPC UA, so it will integrate”Interoperability comes from the companion specification. Without one you have a browsable tree and a mapping exercise.
“A deadband is free compression”It is lossy, irreversible and applied at the source, and on a moving signal it quantises rather than filters (r ≈ v/D).
