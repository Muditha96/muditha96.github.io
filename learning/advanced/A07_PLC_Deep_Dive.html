What a PLC Really Is

A ruggedized, deterministic computer that trades raw speed for guaranteed timing.

Precise Definition

A Programmable Logic Controller is an industrial digital computer that continuously reads inputs, executes a stored user program, and drives outputs in a fixed, repeating loop — engineered for reliability in electrically hostile environments (heat, vibration, EMI, dust).

It replaced banks of hard-wired relays. The genius is not speed — a desktop CPU is faster — but determinism: the PLC guarantees that the loop completes within a bounded time, every single time. That predictability is what makes a machine safe and repeatable.

Born from relays

1968, GM's request to replace relay panels → the Modicon 084, the first PLC.

Deterministic

Bounded scan time. The same inputs always produce the same outputs in the same time.

Ruggedized

Rated 0–60 °C, vibration, 24 V industrial logic, isolated I/O, no fans/HDD.

Why not just use a PC?

A general-purpose OS (Windows/Linux) is non-deterministic — background tasks, garbage collection, and interrupts cause jitter. A PLC runs a stripped real-time executive (a firmware-level scheduler) with a watchdog timer that faults the CPU if a scan ever overruns. In a press or a robot cell, a 50 ms unexpected delay can wreck a part or injure an operator — so bounded timing is a hard requirement, not a nicety.

Hardware Anatomy

A modular rack: power supply, CPU, and snap-in I/O on a shared backplane bus.

A real modular PLC: power supply → CPU → digital in → digital out → analog in → comms, all sharing one backplane bus.

🔌 Power Supply (PSU)

Converts plant AC (or 24 V) to clean, isolated logic voltage. Sized for total backplane current draw.

🧠 CPU Module

Processor + real-time OS + RAM + retentive memory. Holds the program and the process image.

↘ Digital I/O

On/off signals: 24 V sinking/sourcing inputs; relay or transistor outputs.

📈 Analog I/O

Continuous signals via ADC/DAC: 4–20 mA, 0–10 V, RTD, thermocouple.

🌐 Comms Module

Fieldbus & Ethernet: PROFINET, EtherCAT, Modbus, EtherNet/IP.

🧱 Backplane Bus

The rail that carries power + a fast data bus so the CPU can address each slot.

Page 3 · The Heartbeat

The Scan Cycle

The single most important PLC concept. Master this and everything else clicks.

A PLC does not react to inputs the instant they change. It works in a strict repeating loop — the scan cycle — with four phases.

Phase: idle · Scan #0

① Input Scan

All physical inputs are copied at once into the input process image (PII). ~0.1–0.5 ms.

② Program Execute

Logic runs top→bottom, left→right, reading only the frozen image — never live pins.

③ Output Update

The output process image (PIQ) is written to physical terminals in one block.

④ Housekeeping

Comms, self-test, and the watchdog reset. Then the loop restarts.

⚠ The consequence you must internalise

Because inputs are frozen for the whole execute phase, a signal that changes mid-scan is not seen until the next scan. Worst-case input latency ≈ 2 × scan time (one scan to catch it, one to act). This is why a 20 µs pulse can be missed by a 10 ms scan — and why fast events need hardware interrupts (HSC / event tasks), not the normal scan.

Memory & Addressing

Where data lives, and how a tag maps to a physical bit.

The process image — the key idea

The CPU keeps a mirror of the I/O in RAM. Your program talks to this mirror, not the wires. Reading %I0.3 reads a bit in the input image; writing %Q1.0 sets a bit in the output image that gets flushed to the terminal in phase 3.

AreaIEC symbolExampleHolds
Inputs%I%I0.3 / %IW64Image of physical inputs (read-only in logic)
Outputs%Q%Q1.0 / %QW80Image written to physical outputs
Memory / Flags%M%M10.2 / %MW20Internal bits & words (scratchpad)
Data BlocksDBDB5.DBW4Structured user data, recipes, buffers
Timers / CountersT / CT1, C3Timing & counting instances

Bit addressing

%I0.3 = byte 0, bit 3. 8 bits per byte; .0–.7.

Byte / Word / DWord

%IB=8 bit, %IW=16 bit, %ID=32 bit. Words overlap two bytes.

Retentive memory

Battery/flash-backed area survives power loss — for counts, setpoints, totals.

Symbolic tags

Modern IDEs map Motor_Run → %Q1.0 so logic reads in plain language.

Data types you'll actually use (IEC 61131-3)

BOOL (1 bit) · BYTE/WORD/DWORD (bit strings) · INT/DINT (signed 16/32-bit) · REAL (32-bit float) · TIME · STRING. Choosing the right width matters: a flow total in an INT overflows at 32 767 — a classic field bug. Use DINT or REAL for accumulators.

Page 5 · Programming

The 5 IEC 61131-3 Languages

One standard, five notations. Pick the right tool for the logic.

LD

Ladder Diagram

Power rails + contacts + coils. Reads like a relay schematic — loved by electricians, dominant for discrete logic.

// Start/Stop seal-in |--[ Start ]--+--[/Stop]--( Motor )--| |--[ Motor ]--+
FBD

Function Block Diagram

Boxes wired together (AND, OR, PID, timers). Excellent for signal flow and process/analog control.

[ Start ]──┐ AND ├──[ TON ]──( Q ) [/Stop ]──┘
ST

Structured Text

High-level, Pascal-like. Best for math, loops, strings, state machines — compact and powerful.

IF Start AND NOT Stop THEN Motor := TRUE; END_IF;
SFC

Sequential Function Chart

Steps + transitions — a visual state machine. Ideal for batch & sequential machine cycles.

Step1 ─[t:done]→ Step2 Step2 ─[part?]→ Step3 ↺ loop back
IL

Instruction List (deprecated)

Assembly-like mnemonics (LD, AND, ST). Legacy only — removed in the 3rd edition of the standard, but you'll still meet it in old code.

POUs — how big programs stay sane

Code is organised into Program Organisation Units: Functions (FC) — stateless, return a value; Function Blocks (FB) — keep internal state (a PID, a timer); and Programs (PRG) — the top level assigned to a task. Reusable FBs are the heart of clean, testable PLC code.

Page 6 · The Edge

I/O & Signal Conditioning

Where the digital world meets copper, current, and the real machine.

Sinking vs Sourcing

Sourcing (PNP) input expects +24 V; sinking (NPN) input expects 0 V. Mismatch = dead I/O. Match sensor type to card type.

Relay vs Transistor out

Relay: any load, slow, wears out. Transistor: DC only, fast, silent, long-lived. (See lesson 28.)

Analog: 4–20 mA

Current loop is noise-immune & "live-zero": 4 mA = 0 %, so a broken wire (0 mA) is detectable as a fault.

Resolution

A 12-bit ADC = 4096 steps. Over 0–10 V that's ~2.4 mV/step — set engineering scaling accordingly.

Isolation

Optocouplers/transformers keep field surges off the CPU. Galvanic isolation protects the backplane.

Filtering & debounce

Input filter time (e.g. 3 ms) rejects contact bounce & EMI — but adds latency. Tune per signal.

Scaling — the everyday analog task

A 4–20 mA pressure sensor reads 0–10 bar. The card gives raw counts (e.g. 0–27648 on Siemens). You linearly scale: EU = (raw − raw_min) × (EU_max − EU_min) / (raw_max − raw_min) + EU_min. Getting live-zero offset right (4 mA ≠ 0 counts) is where beginners slip.

Page 7 · Reliability

Determinism, Tasks & Redundancy

From single-task scans to fault-tolerant, safety-rated systems.

Cyclic, periodic & event tasks

Beyond the free-running main scan, modern CPUs run periodic tasks (e.g. a PID exactly every 10 ms for stable control), event/interrupt tasks (fire on a hardware edge or high-speed counter), and priority scheduling so critical loops pre-empt slow ones. The watchdog guards every task: overrun → CPU faults to a safe state.

Watchdog

Set ≈ 2× max scan. Overrun = STOP/fault, not silent lag.

Jitter

Variation in cycle time. Low jitter = tight motion & control.

Hot standby

Two CPUs in sync; backup takes over in <1 scan on failure.

Safety PLCs — a different breed

A Safety PLC (F-CPU) is certified to IEC 61508 / IEC 62061 and ISO 13849 (PL d/e). It runs the user program on two diverse channels, cross-checks results, tests its own I/O thousands of times per second, and forces outputs to a safe state on any discrepancy. This is how an E-stop or light curtain is trusted to stop a robot — tying directly into the safety systems of the automation cell.

Page 8 · From the Field

Engineering Practice

Field-proven habits, the failures that actually happen, and senior-engineer notes.

Commissioning tips
  1. 1
    Keep scan time stable. Watch max scan in diagnostics; a creeping number warns of an inefficient loop before it faults.
  2. 2
    Never do edge detection on a slow input. Use a rising-edge instruction (R_TRIG) — and for fast pulses use a high-speed counter, not the scan.
  3. 3
    Structure with FBs. One reusable, tested "Motor" block beats 40 copied rungs. Less code = fewer bugs.
  4. 4
    Force tables are for testing only. Forced I/O left in a running machine is a top cause of "ghost" faults — document and clear them.
  5. 5
    Comment in symbols, not addresses. Conveyor_Jam survives a hardware change; %I0.4 does not.
⚠ Common failures
⏱ Missed fast input

Pulse shorter than scan time is lost — the program never sees it. Fix: HSC / interrupt task.

🔁 Watchdog trip

A runaway loop or huge FOR-loop overruns the scan → CPU faults to STOP. Fix: bound loops, raise limit cautiously.

🔌 Sink/source mismatch

PNP sensor on an NPN card reads nothing. Fix: match sensor & card polarity.

📉 INT overflow

A totaliser in an INT rolls over at 32 767 and jumps negative. Fix: DINT/REAL accumulator.

⚡ EMI false trips

Unshielded analog beside VFD cable = noisy reading. Fix: shielded cable, single-point earth, separation.

🪫 Lost retentive data

Dead backup battery wipes setpoints on power cycle. Fix: monitor battery; use flash retention.

⭐ Pro engineer notes
Read the diagnostics buffer first

90% of "the PLC is broken" calls are answered by the CPU diagnostic buffer — it timestamps the exact fault.

Order matters in ladder

Because logic runs top-down using the live image, a coil set then reset later in the same scan ends OFF. Sequence deliberately.

Version & back up offline

Always keep the source project archived — the running CPU may hold compiled code you can't fully reverse.

Design for the safe state

Ask "what happens on wire-break / power-loss?" De-energise-to-stop and live-zero analog make failures visible.

Quick Check · Active Recall

Q1: A proximity sensor pulses HIGH for 5 ms. The PLC scan time is 12 ms. Will the program reliably detect it? Why?

Tap to reveal ↓ A: No — not reliably. Inputs are only sampled once per scan, during the input-scan phase. A 5 ms pulse can begin and end between two samples and be missed entirely. To catch it, route it to a high-speed counter or an event/interrupt task that doesn't depend on the main scan.

Q2: Why does a PLC copy inputs into a process image instead of reading pins live during execution?

Tap to reveal ↓ A: For determinism and consistency. If an input changed mid-program, early and late rungs would see different values, producing race conditions. Freezing the image guarantees the whole scan sees one coherent snapshot — repeatable behaviour every cycle.

Worked Examples

Four exam-grade numericals, solved step by step.

Worked Example 1 — Scan time & worst-case response

Given: input scan 1.5 ms, program execution 12 ms, output scan 1.5 ms, housekeeping 1 ms. Input cards have a 3 ms hardware filter. Find the scan time and the worst-case input-to-output response time.

T_scan = 1.5 + 12 + 1.5 + 1 = 16 ms worst case: the input changes just AFTER the input scan — it waits almost one full scan to be read, then one more scan to be solved and written: T_resp(max) ≈ filter + 2 × T_scan = 3 + 32 = 35 ms T_resp(min) ≈ filter + 1 × T_scan = 3 + 16 = 19 ms

Discussion: this is why "the PLC runs at 16 ms" understates latency — synchronous I/O always risks the two-scan worst case. Anything that must respond faster (registration marks, fast reject gates) belongs on a high-speed counter, an event/interrupt task, or the drive's own logic — not the main scan.

Worked Example 2 — Analog scaling & resolution (4–20 mA)

Given: a 4–20 mA temperature transmitter spans 0–100 °C into a Siemens-style analog input that maps 4–20 mA to 0–27648 counts. The raw value reads 13824. Find the current, the temperature, and the theoretical resolution.

fraction = 13824 / 27648 = 0.50 current = 4 + 0.50 × 16 = 12 mA temp = 0 + 0.50 × 100 = 50 °C scaling formula: T = (raw / 27648) × (T_hi − T_lo) + T_lo resolution = 100 °C / 27648 ≈ 0.0036 °C per count

Discussion: the 0.0036 °C figure is arithmetic, not accuracy — the transmitter (±0.25% ≈ ±0.25 °C) and card (±0.3% typ.) dominate. Also note the live-zero benefit: raw = 0 means 4 mA (true 0 °C), while a broken wire reads under-range (<4 mA) and can be alarmed — a 0–20 mA loop cannot tell "zero" from "cut cable".

Worked Example 3 — When the scan cannot count: encoder maths

Given: a 1024 ppr incremental encoder on a shaft at 1750 rpm, read in ×4 quadrature. Can a 16 ms scan count it? What hardware is required?

f_pulse = 1024 × 1750 / 60 = 29 867 Hz (≈ 29.9 kHz) ×4 quadrature edge rate = 4 × 29 867 ≈ 119.5 kHz pulse period = 1/29 867 ≈ 33 µs vs scan = 16 000 µs scan-based counting limit ≈ 1/(2 × T_scan) = 31 Hz → hopeless

Discussion: the scan can reliably count only signals slower than about half its rate (Nyquist logic applied to sampling the input image). At 30 kHz the program would miss ~99.9% of pulses. The fix is a high-speed counter module (typ. 100 kHz–1 MHz) that counts in hardware and hands the program a ready total — the program then reads position, not pulses.

Worked Example 4 — Redundant CPU availability

Given: a CPU has MTBF = 100 000 h and MTTR = 4 h. Compute availability for a single CPU and for a 1oo2 hot-standby pair (independent failures assumed).

A_single = MTBF/(MTBF + MTTR) = 100000/100004 = 0.99996 downtime ≈ (1 − A) × 8760 h ≈ 21 min / year A_pair = 1 − (1 − A)² = 1 − (4×10⁻⁵)² ≈ 0.9999999984 downtime ≈ 1.6×10⁻⁹ × 8760 h ≈ 0.05 s / year

Discussion: the pair looks a million times better on paper, but the assumption of independence is the weak point: shared power, a common firmware bug, or a botched switchover (bumpless transfer failing) are common-cause failures that dominate real redundant systems. That is why standards cap the credit you may claim (β-factor, typically 2–10%) — engineered diversity matters more than duplication.

Problem Set — 10 Questions

Work each one before revealing. The scan cycle and the scaling formula do most of the lifting.

Problem 1

An 8 ms pulse arrives at a PLC whose scan time is 20 ms. Detection options?

Tap to reveal ↓ A: The main scan samples inputs every 20 ms, so an 8 ms pulse can fall entirely between samples — unreliable. Use a high-speed counter input, an interrupt/event task, or a pulse-stretching input card. (A latching sensor also works if the process allows.)
Problem 2

Raw value 20736 on a 0–27648 card, transmitter 4–20 mA = 0–16 bar. Current and pressure?

Tap to reveal ↓ A: fraction = 20736/27648 = 0.75 → current = 4 + 0.75×16 = 16 mA; pressure = 0.75 × 16 bar = 12 bar.
Problem 3

Why does ladder logic executed top-down mean a coil written twice ends up controlled by the LAST rung only?

Tap to reveal ↓ A: Outputs are written to the process image, not the terminals, during execution. Each assignment overwrites the image value; only the value present at the end of the scan is copied to the physical output. This is the classic "double coil" bug — the first rung's result is silently discarded.
Problem 4

A production totaliser must survive power loss; a "cycle running" flag must NOT. Where does each live?

Tap to reveal ↓ A: Totaliser → retentive memory (battery/flash-backed), declared RETAIN, in a DINT/REAL. The state flag → non-retentive, so a power cycle restarts the sequence from a known safe state instead of resuming mid-cycle with the machine physically elsewhere.
Problem 5

State what TON, TOF and TP timers each do to a 2 s preset when their input pulses.

Tap to reveal ↓ A: TON (on-delay): output goes TRUE 2 s after input rises, drops immediately with input. TOF (off-delay): output follows input TRUE immediately, stays TRUE 2 s after input falls. TP (pulse): any input rising edge fires a fixed 2 s pulse regardless of input duration.
Problem 6

Draw (mentally) a start/stop seal-in rung. Why is the stop contact wired NC in hardware?

Tap to reveal ↓ A: (Start NO ∥ Motor contact) in series with Stop → Motor coil: the motor's own contact "seals in" the momentary start. Stop is a physical NC button read by a normally-closed circuit so that a broken wire behaves like pressing stop — fail-safe (de-energise-to-stop). A NO stop with a cut cable could never stop the machine.
Problem 7

2048 ppr encoder at 3000 rpm, ×4 quadrature. Edge rate? Suitable input?

Tap to reveal ↓ A: f = 2048 × 50 = 102.4 kHz; ×4 = 409.6 kHz edge rate. Needs a high-speed counter rated ≥ 500 kHz (or the drive/motion controller's encoder port) — no standard DI card or scan-based count survives this.
Problem 8

Give three distinct causes of a watchdog trip, and the first diagnostic you would check.

Tap to reveal ↓ A: (1) unbounded/huge program loop (FOR over a big array each scan); (2) a blocking wait or heavy communication burst extending the scan; (3) an interrupt storm from a chattering event input. First stop: the CPU diagnostic buffer — it timestamps the overrun and usually names the offending OB/task.
Problem 9

A PNP (sourcing) sensor is wired to an input card that expects NPN (sinking) sensors. What do you observe, and what are the two fixes?

Tap to reveal ↓ A: The input never turns ON (or floats erratically) — the sensor sources current to +24 V but the card also expects to be fed from +24 V, so no current flows through the input circuit. Fixes: use a card of matching polarity (or a configurable sink/source card), or replace the sensor. (A pull resistor workaround exists but is poor practice in industry.)
Problem 10

MTBF 50 000 h, MTTR 2 h. Compute availability single and 1oo2, and name the assumption that flatters the second number.

Tap to reveal ↓ A: A = 50000/50002 = 0.99996 (≈ 21 min downtime/yr). Pair: 1 − (4×10⁻⁵)² ≈ 0.9999999984. The flattering assumption is failure independence — shared power, common firmware and switchover logic create common-cause failures that set the real ceiling (handled by β-factor methods in IEC 61508).

Key Derivations & Exam Traps

Where the formulas come from — and the traps that sink real programs.

Derivation 1 — worst-case response time
event happens at the worst moment: just AFTER inputs were read wait for next input scan: up to 1 × T_scan solve + write outputs (that scan): included in the 2nd scan ⇒ T_resp(max) = t_filter + 2·T_scan T_resp(min) = t_filter + T_scan average ≈ t_filter + 1.5·T_scan

Why it matters: the factor-of-two is structural, not implementation sloppiness — any read-solve-write architecture has it. Interrupt tasks beat it by bypassing the image; fieldbus-synchronised I/O (e.g. EtherCAT distributed clocks) beats it by aligning sampling with the cycle.

Derivation 2 — analog resolution & scaling line
an n-bit converter divides its span into 2ⁿ steps: LSB = span / 2ⁿ 12-bit on 0–10 V → 10/4096 = 2.44 mV any linear scaling is one straight line through two points: y = y_lo + (x − x_lo)·(y_hi − y_lo)/(x_hi − x_lo) with (x_lo,x_hi) = raw counts, (y_lo,y_hi) = engineering units

Why it matters: every scaling block (SCL, SCP, NORM_X/SCALE_X) is this one line dressed up. Knowing it lets you scale anything — including reversed ranges (20–4 mA), offset live-zero ranges, and bipolar ±10 V — without memorising vendor blocks.

Derivation 3 — availability algebra
A = uptime/(uptime+downtime) = MTBF/(MTBF + MTTR) series (both needed): A_sys = A₁ × A₂ (availability multiplies DOWN) parallel (either works): A_sys = 1 − (1−A₁)(1−A₂) (unavailability multiplies)

Why it matters: the same two lines size everything from redundant CPUs to dual power supplies to parallel pumps. Series chains punish long systems (ten 99.9% elements ≈ 99.0%); parallel pairs reward even modest elements — until common-cause failure caps the gain.

Seven exam & field traps
  1. 1
    Double coil. The same output written on two rungs — only the last write survives the scan. Use one coil, many conditions.
  2. 2
    Scan-order dependency. Logic that works only because rung A runs before rung B breaks the day someone reorders networks. Make state explicit.
  3. 3
    INT overflow at 32 767. Totals and encoder counts belong in DINT/REAL; a rolled-over INT jumps to −32 768 mid-production.
  4. 4
    Floating-point equality. IF Real_A = Real_B is a coin toss after arithmetic — compare with a tolerance band.
  5. 5
    Forces left on. A forced output overrides all logic silently, surviving downloads on many platforms. Check the force table before any "impossible" behaviour hunt.
  6. 6
    BCD vs binary. Legacy thumbwheels/displays speak BCD; treating 0x25 as 25 decimal (it is 37) corrupts every setpoint. Convert explicitly.
  7. 7
    Units in scaling. Mixing raw counts, mA and engineering units in one formula is the top analog bug — write the two calibration points as a comment above every scaling block.

Hands-on ladder — eight exercises
  1. 1
    Seal-in first. In CODESYS, build start/stop with seal-in, then add an interlock and a run-hours totaliser (DINT, RETAIN).
  2. 2
    Timer trio. Implement the same 3 s delay with TON, TOF and TP; watch all three on a trace and explain the differences in one sentence each.
  3. 3
    Break the scan. Write a deliberate double-coil bug, observe it, fix it. Then create a scan-order dependency and refactor it away with explicit state.
  4. 4
    Scale analog by hand. Code the two-point scaling line in ST for a 4–20 mA level sensor, including under-range (broken wire) alarming below 4 mA.
  5. 5
    State machine. Build a 4-step sequence (fill→heat→hold→drain) in SFC, then rebuild it in ladder with an INT step register — feel why SFC exists.
  6. 6
    Measure your scan. Read the CPU's min/avg/max scan diagnostics, then add a 10 000-iteration loop and watch the watchdog margin shrink.
  7. 7
    Simulate a fast pulse. Feed a 5 ms pulse generator into a normal input vs an HSC/event task; log how many each catches in 1000 pulses.
  8. 8
    Write the FB. Package "Motor" (start/stop/fault/hours) as a reusable function block with a declared interface, instantiate it three times, and version it.
